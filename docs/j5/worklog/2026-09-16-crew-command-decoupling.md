> **Record.** How `/crew` stopped depending on a `crew-captain` saved agent, how a Captain came to command several named Crews at once, and what the review of the Crews stack (PRs #145 to #152) changed. Accurate about 2026-09-16 and 2026-09-17; the current behavior is in [Crews](../product/features/crews.md).

# Crews: /crew without a Captain persona, and one Captain with many Crews

## 2026-09-16 — the command carries the guidance, not a persona

Until this session `/crew <brief>` worked only on a fresh draft: the draft launched as the saved agent with id `crew-captain`, whose instructions taught it to read the library, propose a roster, and end its turn. A library without that agent refused the command. Bryant asked to decouple the two: the command should still review the ask and file a Crew proposal for the person to decide, but through whatever agent the thread already runs as.

The `/crew` send path now wraps the brief in a short platform block (`<j5_crew_launch>`) that says only what the tools cannot: compose rather than work, end the turn after proposing, and that several Crews may run at once. The `propose_crew` and `request_crew_member` descriptions and the `<j5_crew_gate>` notice describe the rest. The thread keeps its own agent, model, and policy; any thread, fresh or mid-conversation, can become a Captain, so the fresh-draft refusal and the library check are gone and the slash menu offers `/crew` in every composer. The bundled `crew-captain` example, its built-in id, and the persona-library page's section on it were removed with the coupling rather than left as a second, drifting copy of the guidance.

## 2026-09-16 — one Captain, many Crews

Bryant also asked that a single Captain be able to run more than one Crew when the work is concurrent, and that each Crew be named and have its own expand and collapse. The server already allowed this: proposals never checked for an existing Crew, `request_crew_member` disambiguates by `crew_instance_id`, the archive cascade retires every Crew a Captain commands, and the Fleet page grouped seats per Crew. The sidebar expander did not: it folded every child under one "N crew" toggle and offered Stop only when every child belonged to one Crew.

The expander now groups a Captain's children by Crew, newest activity first, one collapsible header per Crew with the Crew's name and its state summary, plus one more group for solo Peer Agents the row spawned outside any Crew. Stop sits on the Crew header it stops. Expansion is remembered per group under its parent. The Crews definition gained a Captains bullet for concurrent Crews and a scenario with two Crews under one thread, and the `propose_crew` description tells the Captain to name each Crew for what it is for.

## 2026-09-16 — the notices become cards

With the guidance riding in the `/crew` turn, the person's own message showed the platform block in its bubble, and the Captain's thread already showed `<j5_crew_gate>` and `<j5_seat_settled>` as raw tagged text. Bryant asked to hide them unless they could be shown well. The web timeline already hands every user-role row to a J5-owned delivery renderer for A2A envelopes; the three Crew notices now ride that same seam and render as cards: the brief as the brief with the guidance one click away, the gate decision as its title, Crew name, and roster with each seat opening its thread, and seat finishes one row per seat with the run's end and the handoff's state, the handoff opening in the artifacts panel and readable inline when short. Recognition is strict, so an unparsed block stays raw, and the gate and seat notices gained the Crew's name so a Captain of several Crews reads which one each card is about. Mobile has no delivery seam and keeps showing these notices as text, as it does A2A deliveries.

## 2026-09-16 — no parent-child permission ceiling

Jackson's review of PR #147 found the escalation guards incomplete: the read-only-parent check and the approvals-on check ran only when `spawn_agent` named a saved agent, a plain spawn copied the parent thread's stored runtime mode, and `delegate_task` had no counterpart. Rather than extend the guard to every child-creation door, his ruling was to take it out. J5 does not carry upstream's strict parent-child model, and a rule that must be enforced identically at every door is one A2A message to a trusting peer away from bypass. A child's permissions come from its own saved agent's policy or from the human's approval, never from the parent. The guards, their test, and the doc sentences that promised a ceiling were removed; the 2026-09-14 record's pre-push review still lists that guard as a fix that landed and now points here.

## 2026-09-17 — the stack review, and three decisions

Jackson reviewed PRs #148 to #152 with the whole stack in view. Most findings were fixed as filed: single-line Crew names and lowercase-hyphen seat names so a name cannot forge the roster lines the Captain's card parses; the seat cap reported as a cap, not a permission; a same-name seat under a different identity refused inside the reservation transaction; no seat added to a retired Crew; the `/crew` turn keeping its attached contexts and surviving the Claude effort prefix; the Fleet poll re-reading only the rows the roster names as involved, with negative answers cached and unchanged batches keeping their snapshot; seat notices keyed by participant (one Captain's Crews reuse seat names), carrying a handoff digest so a rewritten over-limit body still reads as changed, escaping their own opening tag, and committing before the seat settles; Stop crew and Archive crew failures shown as toasts. Three findings needed a design choice, and Bryant made them:

- **Where the lone-seat rule lives.** The rule that a Crew member is never archived alone was on the web preflight and the MCP verb only, so a mobile swipe partially archived a live Crew. Every client door sends its archive as one `dispatchCommand` over the socket, so Bryant chose a J5-owned guard on that one server handler over mirroring the preflight on mobile (which covers no future door) or reversing the archive after the fact (which is not a refusal, flickers, and has to tell a unit archive from a lone one). The guard covers `thread.delete` as well as `thread.archive`, since deleting a lone seat leaves the same partial Crew and is harder to recover from. It is one appended line in the upstream handler; the check itself, its error, and its test are J5 files (`crewSeatArchiveGuard.ts`, FORK.md case 37).
- **One reconciliation pass on boot.** The Captain cascade and the settler ride a stored-event stream that resumes from its high-water mark and log rather than retry a failure, so a cascade that failed on seat two of four, a notice that failed to reach the Captain, or an archive that landed during a restart was never caught up. Bryant chose one sweep at daemon start over persisting and retrying each reaction: live Crews whose Captain thread is archived or deleted retire, and live seats whose newest run finished with nothing settling them settle and tell their Captains. A notice that fails now leaves its seat unsettled on purpose, so the sweep or the seat's next finish retries it.
- **The Crew record comes first.** A roster launch created seat threads before the Crew record existed, so a spawn that failed partway left homed, placed, unbriefed Peer Agents no record knew and a decline abandoned them. Bryant chose recording the instance first, with every planned seat under its deterministic ids, over retiring whatever a failed launch created on decline without a record: the gate is handed back with the human's edited seats kept, a retry converges on the same seats (a renamed seat's stale reservation is dropped), and a decline archives the seat threads that exist and stamps the record retired.

## 2026-09-17 — the second round

Jackson read the fixes and the stack again, this time with the app open. Most of what he found was taken as filed: the `propose_crew`, `request_crew_member`, `stop_crew`, and `archive_crew` descriptions are shorter (long MCP descriptions eat every agent's context on every turn), say "user" rather than "human", and no longer call an archive permanent, since seat threads can be unarchived; `spawn_agent` names its `agent` parameter instead of using "agent" for two things in one sentence; the Captain badge is an anchor mark with the commanded Crews in its tooltip, because the sidebar card had run out of room; a seat thread is titled by its seat alone, since the badge beside it repeated the crew-qualified title; seat rows in the expander mirror the parent card, time on top and provider below; and the roster card's third field is the new seat's instructions on its own line, which is what a person adding a seat needs to say. Three findings were decisions, and Bryant made them:

- **Agents are told about Crews.** An agent asked to "spawn a crew" without the `/crew` prefix made provider subagents, because the standing orchestration instructions described two shapes of help and never a Crew. Jackson proposed a three-option list (Subagent, Peer Agent, Crew) for the shared instructions file, an authorized wording change under FORK.md case 8. Bryant took it; the `/crew` launch block shrank to the one sentence those instructions do not carry (compose rather than work, then end the turn), and the test pins the Crew bullet.
- **The platform settles no seat.** Seats were settled the moment they finished with nothing owed, so a Crew read "2 settled" seconds after launch. Upstream settles a thread by hand, on a merged pull request, or after idle days, and Jackson asked whether we were settling too early. Bryant's ruling: stop settling, keep the notice, and rename the machinery to what it does. The settler is the seat finish notifier, the notice tag is `<j5_seat_finished>`, and upstream's settle rules apply to seats as to any thread. The state summary still counts a seat the person settled.
- **Seats without a saved agent.** Jackson wants a Crew to seat an agent that has no saved definition, so a dynamic Crew need not fit a mold. Bryant agreed and chose a PR on top of the stack rather than growing #148 again: a custom seat is named and briefed on the card (Custom agent is the first option in the agent list, and choosing it asks for the seat's name and instructions) or proposed by the Captain with no agent id, and it runs on the Captain's own provider and model with the Captain's runtime mode, since it has no policy of its own and the human approved it.

## 2026-09-17 — personas, not agents

Jackson's review kept reaching for "persona" where the descriptions said "agent" (`list_personas`, a `persona` parameter), and the same word was doing two jobs: a running participant and a saved definition in the library. Bryant settled it: a library entry is a **persona** everywhere a person or a model reads the word, and "agent" is reserved for something running. Settings → Personas lives at `/settings/personas` (the four current users re-find it; the search entry still answers "agents"), the library panel, dialogs, composer pickers, and the crew card say persona, a seat with no persona is a **custom seat**, and the mention is `@persona:id` with `@agent:id` still parsing. The MCP surface renamed with it, in the same PR, since the stack is unmerged: `list_agents` became `list_personas`, the `agent` parameter on `spawn_agent`, `delegate_task`, and crew seats became `persona` with the old spelling accepted for one release, and crew results carry `persona_id`. Code identifiers, file names, RPC names, and `agent-personas.json` were left alone on purpose: the rename is about vocabulary people read, not internals.

Still open from the review, filed separately by Jackson: a J5 change stream to replace the three foreground polls (inbox count, proposals, fleet). Left as noted: `stop_crew`'s retry safety is tested against a mocked interrupt only; the deterministic command ids are the promise, and the real duplicate-command replay is not exercised.

## 2026-09-18 — the recovery path, rounds three and four

Jackson kept reading the recovery path after the record-first reorder, and each round found the gap the previous fix opened. Round three: the decline was recorded before its cleanup, so a seat archive the store refused left a declined proposal nobody could retry over seats that lingered; releases went by the last approved names, so an addition renamed between two failed attempts left its first reservation; the launcher's retry skipped rows that already had a home, so a seat renamed on the card lingered with a thread and no brief; and the card still seeded from the requested seats, so a failed launch cost the person their edits. All four were taken: cleanup first, release by identity (every row a proposal minted derives from the proposal id), retire dropped or renamed seats before the retry records its roster, seed from the approved seats.

Round four found that the reorder had made the two decisions asymmetric: approve claimed the proposal and then launched, decline cleaned up and then claimed, so two devices resolving the same reopened gate at once could have the decline retire the Crew the approval had just launched, and the previous order had the mirror problem. Bryant took Jackson's shape: every resolution claims the row first, compare-and-set from open into `approving` or `declining`, does its work, and writes the final status last; the second resolver finds the row claimed and is refused. A claim the server lost mid-way is settled by a boot sweep, a declining proposal finished and an approving one handed back, since a launch converges on a retry. The same round caught `Effect.option` on the seat-thread reads, which read every storage failure as "no thread" and dropped rows from under live threads; only a genuine not-found passes now. On the sidebar, the retired-Captain re-read of round three never reached the poll that matters, because the badge read filters retired Crews on the server; rather than pay for retired rosters every tick, the poll re-reads every row still showing a chip, which is exact and costs nothing extra on the wire.

Left as noted for a later change: a seat dropped in one retry and reintroduced in the next reuses its deterministic ids against a thread the earlier retry archived, and nothing unarchives it.

## 2026-09-18 — the fifth round: one launch report

Jackson dogfooded a three-seat Crew with the Claude subscription signed out and posted the sequence the Captain saw: "approved, here is your roster", then, folded into one message, two seats "finished" with a failure line among handoff lines and no reason, then the silence detector's "errored" notices on the asks the Captain had already sent, with the reason at last, framed as a messaging problem. The Captain answered the failures with "no problem" and reported them only when asked; nothing reached the person, because a dead seat read as idle on the Fleet row and the expander. His request, taken whole: one launch report instead of three channels.

- **The gate notice waits for liftoff.** Dispatching a brief commits intent, not a running seat. A launch reporter now watches each seat an approval launched, taking a verdict from what the seat thread already shows and then from run updates on the stored-event stream, until every first turn is running or ended without running, or a 60 second window closes. One `<j5_crew_gate>` report then reaches the Captain: what the person changed against the proposal (added, removed, renamed seats), and per seat started, failed with the run's recorded error, or not started. The proposal records when it was reported, and a boot sweep reports any approval the server lost mid-report. The decline is told at once, as before.
- **Failures at launch are launch outcomes, not finishes.** The finish notifier stays quiet about a failed first turn the report is about to carry, and the notifier's stream feeds the reporter so one stream serves every Crew reaction.
- **A finish leads with how it ended.** The seat notice opens with the run's status and, for a failed run, its recorded error; the card is titled by what ended how. A failed run is reported whatever the seat still owes.
- **One death, one telling.** The silence detector no longer posts an errored notice about a seat to the Captain that commands it; the report or the finish notice already said so, with the reason.
- **A dead seat reads as failed**, on the Fleet row and in the expander, ahead of anything it may still owe the person.
- **The refusal names its reason.** A seat whose provider is signed out, disabled, or missing was already refused at spawn by the persona route; the refusal now says "codex is signed out" rather than "unavailable". Jackson's puzzle, how signed-out seats spawned at all, most likely sits in a cached authenticated status with an expired token; the check itself was in place.

Left for a later change: a bell or inbox entry when a launch failure is one only the person can fix, which needs a platform-authored ask and a sender for it; and the duplicate Setup joke, which only the ledger on Jackson's server can settle.
