# Personas

Agents a task has launched appear in the **Lineage** section of the thread details panel and as subagent cards in the conversation. A child launched as a persona shows its persona chip beside its row and beside its card.

Persona definitions are separate from runtime activity, so only agents that have actually launched appear there.

## Starting a task as a persona

In a new task, the composer offers a **Persona** control beside the model picker whenever the selected environment has launchable personas. Choose one and the model and reasoning controls are replaced by the persona's name and the model it will start on; use the **×** control to go back to a regular task before sending. On mobile, the chosen persona appears in its own row under the checkout row, and the input row stays free for your message. On send, the server resolves the persona's route and pins it to the thread, so the thread shows the same persona chip afterwards. If the persona's definition changes later, the chip shows **Changed**; the running task keeps the definition it started with, and a new task uses the current one.

Threads launched as a persona show the persona beside their home in the thread list, and delegated children show which persona ran them in the Lineage section and on their subagent cards.

## Switching a worker's model

On a started persona task, the composer shows the model picker beside the persona chip; on mobile, tap the persona or its model. Pick another model or provider and send: the next turn runs on it, with the same instructions and access. Anyone who can send messages in the task can switch it.

The switch is checked first: a signed-in provider must offer the model and its options, and that provider must enforce the persona's access level (see the table under [Persona library](#persona-library)). Any model that passes is allowed, even one outside the persona's list, and a reviewer can be moved onto the model that wrote the work. A refused switch says why, and the worker stays on its model. A message you queue while the worker is busy switches it when that message starts. Moving to another provider hands the conversation over as it does on any task. The persona chip's tooltip names the model the worker runs on now, and says when a person changed its model or reasoning.

Agents can't switch a worker's model. An agent that wants another model replaces the worker instead: it starts a new one with the model it wants, or, as a Captain, adds a member.

## Persona library

To run a persona inside a conversation, type `@persona:` followed by its ID, or type `@` and the start of the persona's ID or name; matching personas appear above the file results. Choosing one inserts the mention, and the next message runs that persona as a subagent of the conversation.

Open **Settings → Agent Setup** on web, desktop, or mobile to see the reusable personas in a connected environment. Select an environment to inspect its library and ordered model lists. Personas can be authored in folders and shared through git. J5 Code adds no bundled personas; the library is empty until you create or import personas or add a source folder. A personal persona is already available across all projects on its environment. To share a persona created in Settings through a git-backed library, export its YAML into that repository and configure each environment to read its local clone. Provider credentials, available models, and on/off settings stay local to each environment.

To create a personal persona without writing a file, use **Create persona** beside **Personas**. Give it a name, a stable ID for `@persona:` mentions, a one-line description, markdown instructions, an access level, and an ordered list of models. The persona is stored in the selected environment as an imported definition, so it can be edited, switched off, or removed like any import. Instructions describe behavior; only the access level is enforced. **Full access (unsandboxed)** removes the sandbox: the persona runs with full access on every supported provider, so it can use the network and run any command, and nothing but its instructions limits what it does.

Personas have one access level:

| Access          | Providers that enforce it |
| --------------- | ------------------------- |
| Read-only       | Codex, Claude             |
| Workspace-write | Codex                     |
| Full-access     | All supported providers   |

Turn on **Independent reviewer** for a persona that reviews other agents' work. It then prefers a model that didn't write that work: by default, the work of the conversation that starts it and that conversation's subagents, or in a crew, the members that aren't reviewers themselves, including members the Captain replaced. If only the author's model can run, the reviewer still starts on it, and its first message says it runs on the same model as the author. If some of the work was done by a provider's own subagents, whose models J5 can't see, it says the authors are partly unknown. It's a preference, never a block: no task waits or fails because of it. A model you choose yourself on a crew's roster card is used as is.

Restricted personas run on Codex, or on Claude when read-only. Model entries on other providers are marked in the editor and skipped at launch. Full-access adds no J5 sandbox restriction; provider instruction support still applies.

The list can contain one model or several, each with a provider account and its model options. Add model chooses the first unused model whose provider enforces the selected access level; it is unavailable when none remain. Add, remove, or reorder entries to set your preference, and choose each model's reasoning level when it offers one. A launch uses the first entry whose provider is signed in, offers the model and options, and enforces the access level. A provider with a reported exhausted quota and a future reset is skipped. Only known account-wide quota windows count; model-specific windows and missing reset times do not block a launch. A started task keeps its model unless you switch it (see [Switching a worker's model](#switching-a-workers-model)). If it hits a usage limit, it waits under the usual continuation behavior and never switches models on its own.

To import definitions written as files:

1. Open **Settings → Agent Setup** and select the destination environment.
2. Use **Import** beside **Personas** (on mobile, the **Import persona file** and **Import a folder of personas** rows under the list). Choose **Folder** to include all YAML definitions (`.yaml` or `.yml`) in that folder and its subfolders (hidden folders and `node_modules` are skipped), or **Import → Persona file** to select one YAML file. On web and desktop the picker browses the selected environment's filesystem, the same picker **Add folder** uses; on mobile it opens your device's file picker. Other files are ignored. Each file must contain one persona definition with its own unique ID.
3. The library refreshes after a successful import. Import and removal results appear as temporary toast notifications. A selection can contain up to 50 definitions, each at most 64 KiB. If any definition is invalid, none of the selection is imported; the error identifies the file.

Definitions are YAML files. Use `instructions: |` followed by indented text for multiline instructions. Keep one definition per file; JSON files are not imported.

Older clients can still read the persona library; update the client to see the full ordered list and each entry’s blocked reason. Existing definition files keep loading after an upgrade. Definitions can also use an ordered model list and one `access` level: `read-only`, `workspace-write`, or `full-access`. Older clients can view these personas and continue existing tasks; creating or editing personas requires an updated client. Export and reimport YAML to preserve the full definition. A legacy default of `critic-review` maps to read-only, and `critic-fix` maps to workspace-write. Defaults of `diagnostic` or `publish-only` need one of the three supported levels before new tasks can start. Running tasks retain their saved instructions, model, and access.

Definitions are copied into the selected environment's library. To bring a persona over from another connected environment, use **Copy to environment** instead. Later changes to the original files require another import. If any selected persona IDs already exist, a confirmation lists the affected personas. Each conflicting persona has a replacement toggle, initially on. Turn it off to skip importing that persona and keep its current definition. Choose **Import selected** to import new personas and overwrite the selected existing personas, including local edits, or **Cancel** to import nothing. Turning off every replacement still imports any new personas in the selection. Replacement preserves each persona’s on/off setting and existing tasks; future launches use the imported definition. Original source files remain unchanged. If an existing definition changes while confirmation is open, you will be asked to confirm again. Duplicate IDs within the same selection are always rejected.

Each persona shows its availability badge (hover a **Blocked** badge on web or desktop, or read the line under its name on mobile, to see why each model entry failed: a model the signed-in provider does not offer, a provider that is not signed in or has reached its usage limit, or an access level that is not enforceable yet) and its origin (**Personal** for created or imported personas, or **Folder** with the source folder's name). Once a persona has launched a task, a usage line appears under its description (on mobile, in the status line under its name): tasks, runs, completed and failed counts, the average run time, tokens reported by the provider, and the last launch date. Hover the line (web and desktop) to see which models those tasks actually ran on. The numbers are read from the environment's existing task history whenever Settings opens, so nothing extra is stored. Every listed persona has an **On/Off** switch, including folder personas. New imports start on. Turn a persona off to keep it in the library while preventing new launches; its status changes to **Disabled**. Turn it back on to make it available for activation, subject to its model and access-level requirements. The setting belongs to the selected environment and survives restarts and edits; switching off a folder persona never touches its file.

To remove a persona whether it is on or off, choose **Remove** from its row's **⋯** menu. Removing an imported or personal copy deletes it, so it must be imported again to come back. A removed folder persona stays in the list marked **Removed** with a **Restore** action that brings it back. Source files remain unchanged, removal survives restarts, and running tasks keep their saved definition.

To edit an imported or personal persona, choose **Edit** from its row's **⋯** menu, or tap its row on mobile. You can change its **Name**, **Description**, **Instructions**, **Access level**, **Models** with their reasoning settings, and **Independent reviewer**. The same menu also has **Duplicate as personal persona**, which opens the create dialog prefilled from that persona with a fresh ID (the way to customize a folder persona), **Export YAML**, which downloads or shares the definition as a file another environment or teammate can import, and, when more than one environment is connected, **Copy to environment**, which imports the same definition into the environment you pick. Copying uses the ordinary import path, so an existing persona with the same ID in the target asks for confirmation before it is replaced. Open the model menu to see every signed-in provider and its models, such as Cursor, OpenCode, and Pi. A persona only launches on a provider whose sandbox enforces its access level; on other providers it shows as **Blocked**. The editor lists those providers under **Access level** and names any chosen provider that can't sandbox it. The access level controls only the sandbox, so write anything the persona should not do, such as committing or merging, into its instructions. Hover over a provider to open its models in a side submenu (tap on mobile). Reasoning stays in a separate control showing all options supported by the selected model. Model choices come from the selected environment. Previously configured values are retained until you change them, including unavailable models and other reasoning levels. Save updates only the imported copy and preserves its on/off setting. Cancel discards the draft. Changes affect future launches; the original file and existing tasks stay unchanged. Import a copy first to edit a folder-loaded persona. The persona ID stays fixed.

To invoke a persona in Codex or Claude, type **@** in the composer and select a persona, or type `@persona:<id>` directly. For example: `@persona:scout review the authentication flow`. Available personas come from the current environment. You can remove a selection by deleting its mention before sending.

The selected persona runs as a subagent under the current conversation and returns its result there. It uses its saved instructions, ordered model list, reasoning, and access level, even if its model uses a different provider from the parent. A persona you pick gets its saved access, even when the conversation runs in Supervised or as a read-only persona. Only a mention you type in the message that starts the agent's turn counts as your pick; a mention you send while the agent is already working, one another agent relays, or one in a scheduled task is the agent's pick. Agents can also choose a persona on their own when one fits. A persona an agent picks can't have more access than the agent runs with, and uses only the models **Models for custom members** checks; if none qualifies, the agent asks you (see [When a persona can't start](#when-a-persona-cant-start)). Running subagents keep their saved definition when the library changes. Crews and new-task crew launches are not part of persona invocation.

An agent can also start a persona as a peer with its own top-level task by naming it in a spawn. The peer keeps the persona's instructions and access level. The server picks the model from the persona's list unless the spawning agent pins one, which must match one of the persona's declared provider instances and models. A pinned model that can't run stops the spawn; it never moves to another entry. A declared reasoning level must match; when the entry leaves reasoning unspecified, the spawner can choose a supported level. Models without a reasoning option omit it. The peer runs with its own persona's permissions, not the spawning agent's. When you name the persona with `@persona:` in the message that starts the agent's turn, any persona can be started this way. When the agent picks the persona itself, the persona can't have more access than the spawning agent runs with, and the model it names must be checked in **Models for custom members**. An agent connected from outside J5 is held to the level you approved it for. The library marks Full access personas.

## When a persona can't start

A persona that can't start stays blocked: the agent never recreates it as a plain or custom agent to get around its limits. The refusal says why: the library is empty or can't be read, there's no persona by that name, it's turned off, its definition is invalid (with what to fix), or none of its models can run, with a reason for each one.

The agent then asks you, so the request reaches your Inbox. In a crew, a member tells its Captain, and the Captain asks you; the request also appears above the Captain's composer. J5 adds its own record of what blocked the launch to the request.

When one limit stood in the way, either a model **Models for custom members** doesn't check or broader access than the asking agent runs with, an Owner sees **Allow this once** on the request. It answers the request and lets one launch attempt past that limit; the agent then retries it. If that attempt fails, the agent asks you again. It never changes the persona, and the next launch meets the usual limits again. A provider that can't enforce the persona's access is never allowed, even once. Collaborators see the request and can reply in words, which allows nothing. **Allow this once** is on the web and desktop apps; the mobile app shows the request without it.

## Crews

A crew is a group of agents that one agent, the Captain, runs as a unit for one piece of work. Ask the agent in your current conversation to put a crew together, using ordinary chat. Ask for a crew and you get one. If you don't ask, the agent decides from the work whether a crew fits: it uses one when the workers must respond to each other, such as a builder and reviewers going back and forth on a change, and hands independent pieces to subagents instead. For example:

> Put together a crew to follow @docs/runbooks/release.md for the 2.4 release and report back when the PR is green.

The agent uses the conversation to propose a roster above the composer. Each member has a responsibility, a reason for joining, and instructions. Members may use saved personas or be custom agents created for this task. You can remove members, add a saved persona, or add a custom seat with a name and instructions, then approve or decline. Custom members start with the Captain's harness, model, and reasoning level, and with Full access, as long as that model and level are ones **Models for custom members** allows. When a roster is approved automatically, or the Captain adds a member, no member gets more access than the Captain runs with: a custom member with no access set gets the Captain's instead of Full access, and persona members use only the models **Models for custom members** checks. Before approval, you can change their harness, model, reasoning level, and access, whether the agent proposed the member or you added it manually. Selecting a saved persona uses that persona's configured access level. No special Captain persona is needed, and one Captain can coordinate several crews in the same conversation. Before you approve, each member shows its resolved harness, model, reasoning level, and access. Members whose access asks before acting are marked **Stops for approvals**: they pause in their own threads until you answer, so give them Full access if you will not be watching. Changing the roster refreshes these details. If the configuration changes before launch, review the refreshed settings and approve again. The preview also covers the Captain's branch and worktree, so switching the Captain's branch before you approve means reviewing a fresh preview. Each member also shows where it works, chosen by the Captain for every member it proposes: **Captain's checkout**, a **New worktree** from a base branch, or an **Existing worktree** of the project. You can change any member's choice before approving. A new worktree offers a searchable branch list, starting at the Captain's current one, with an option to start from the branch's copy on origin; an existing worktree offers the project's worktrees. A member you add yourself starts in the Captain's checkout. A new worktree's setup script starts with it, and unless the script is set to finish first, the member may begin before it does. If preparing a member's worktree fails, the Captain is told why in the launch report. A member on an ACP registry harness offers only **Supervised** and **Full access**, because those harnesses can't enforce **Auto-accept edits** or **Auto**.

To let Captains launch new Crews without reviewing the initial roster, open **Settings → Agent Setup → Crews** and enable **Auto-approve new Crews**. It starts off. Use the settings scope to set an environment default or a project override. Changing it leaves existing Crews and open proposals alone.

To choose which models and reasoning levels custom members may use, open **Settings → Agent Setup → Crews → Models for custom members**. The row reads, for example, "6 of 12" models; open it to check or uncheck each model and each reasoning level of the providers you have set up. Until you save a list, everything is allowed, and after you save one a model or level added later starts unchecked. If no model is checked, no custom member can start, and the row says so; with no level checked, custom members can't use models that have levels. The same lists apply to custom crew members, whether you or the Captain added them and whether the crew launched automatically, and to agents started without a persona by another agent. A custom member's model and reasoning pickers on the roster card offer only the checked entries, and one that isn't checked is refused with the ones that are. Set an environment default or a project override like **Auto-approve new Crews**. Personas you pick, with an `@persona:` mention, from the composer, or on a roster you approve, run on their own model and level, even ones that aren't checked; the row names any persona whose model isn't. Personas an agent picks on its own use only checked ones. The list doesn't cover native subagents, which Codex, Claude and Cursor start on a model of their own choosing.

A crew can follow a playbook: ask for one by name, and the Captain assigns each member the steps it owns. The roster card then shows the playbook, which member owns which step, the steps no member owns (the Captain does those), and any step whose persona differs from the member's, including when the wanted persona doesn't exist on this server. A persona that's turned off, invalid, or can't run isn't replaced: the Captain keeps its steps and asks you about it. On the roster card you can't move steps between members; removing a member there leaves its steps unowned, and the card tells you. Once the crew runs, the Captain moves steps only by replacing a member, as below. If the playbook or a persona it names changes after you open the card, approval asks you to review again.

The Captain can add a member to a running crew without asking you, and can replace one, for example to move a reviewer off the model that just wrote the work it reviews. The new member takes over the replaced member's unfinished playbook steps, including a step already handed to it, and starts with a pointer to the old member's conversation; the steps it finished in the crew's current playbook run stay with it. The replaced member is stopped and leaves the crew; Fleet and the Captain's toggle show it as **Replaced by** its successor, and its conversation stays readable. It works as an ordinary agent until the crew is archived, which archives it too. If the new member can't start, the original member keeps its seat and its steps and carries on. When a crew comes back with its Captain, a replaced member's conversation comes back too, but it stays replaced and doesn't rejoin the crew.

A conversation on any harness can propose a crew. On **Codex** and **Claude**, the roster is the only Crew approval when auto-approval is off. With auto-approval on, it launches directly. Other harnesses may show their own approval prompt once before the roster, and a conversation running as a saved persona with read-only access can't propose a crew on them. Two cases differ:

- **Cursor** proposes a crew only when the conversation runs in **Full access**. In other modes, a Cursor team admin can add the t3-code tools to the team's MCP tool allowlist.
- An OpenCode conversation on an external server cannot propose a crew.

Members can talk directly to each other and their Captain, and Captains can coordinate with other Captains. They share findings, questions, blockers, and results as messages while work continues; creating a report is not a prerequisite for communication. Active Codex GPT 6 and Claude runs take peer messages during work; other models and providers queue them for the next safe turn boundary.

When a member needs help, it tells the Captain. The Captain can add another member directly, explaining the gap and assignment. No approval is needed for additions. Provider sign-in, capacity, and member configuration checks still apply; each member's access still controls its tool approvals in the Inbox. Existing addition requests from an older version can be approved or declined above their Captain's composer.

When a crew member needs your approval to use a tool, the request appears under **Crew agent requests** in the Inbox and counts on the Inbox badge, so you can approve or decline it without opening the member's conversation; it also stays in that conversation. The Captain's own tool approvals and native questions appear in the Captain's conversation, where you are working with it. Crew members take their questions to the Captain rather than to you: a member that needs a decision asks its Captain, which answers, or asks you when it needs your judgment. That question is pinned above the Captain's message box with a place to reply, and it is listed in the Inbox too; answering in either place answers both. Members running on Claude or Codex have native questions suppressed; on other harnesses they are instructed not to ask natively. If a native question still arrives from a live member or a solo Peer Agent started by J5, it appears under **Agent questions** in the Inbox. Open it to answer in the agent's original conversation. Its Captain or parent agent is notified when available. Native-question answers do not record who answered. If you need a record of who answered, ask the agent to send its question to your Inbox instead, and reply there. The mobile app has no Inbox yet, so approvals and questions remain in the agent's conversation.

Every member is instructed to send its result, evidence, and unresolved issues to the Captain. Completion notices tell the Captain how the member's run ended and carry the member's reply, cut when it is long (the rest is in the member's own conversation). The Captain's conversation tells you only about members that need you: one that couldn't start or failed. A persona does not owe a file; if an assignment asks for one, the member writes it as a project artifact and it appears on the Artifacts page.

Crews are a web and desktop feature; the mobile app shows crew members as ordinary agents and has no roster gate. Members stay out of the thread list so it shows the conversations you started; the Captain's row shows an anchor mark (hover it for the crews it commands) and, for each crew it runs, a toggle named for that crew that opens into its members with seat, status, and last activity; agents it started outside a crew get a toggle of their own. When a member finishes and owes no reply, the Captain is told how it ended; the member's thread settles under the same rules as any other thread, and settling the Captain settles its crew's members, except any still working or waiting on you. **Fleet**, from the radar icon beside the Inbox, shows every agent by project with each crew under its Captain.

To stop a crew that is heading the wrong way, use **Stop crew** on the crew's row in Fleet or the small **Stop** beside that crew's toggle under the Captain in the thread list; both appear only while a member is running. Stopping interrupts every running member's turn and nothing else: members stay on the roster and can be messaged again. The Captain can do the same from its own tools.

A crew is retired as a unit, by the Captain or by you. The Captain is shown exactly what will end, seat by seat, and asked to confirm; the guidance is to check with you first. You can retire a crew yourself with **Archive crew** on its row in Fleet. A crew always follows its Captain: archiving a Captain's thread retires its crews with it (from the thread list, a dialog first lists every member with any running turn or open ask), and unarchiving the Captain (or **Undo** on its archive) brings those crews back, though not the turns the archive interrupted. If some members come back and the crew still shows as retired, archive the Captain again and unarchive it. Settling or unsettling a Captain does the same to its members. A crew you retired with **Archive crew** stays retired. Individual crew members cannot be archived or deleted on their own, from any device. Archiving a crew removes the worktrees it created for its members when they are clean and their work is merged, and keeps any with unfinished work. Members the Captain replaced are archived with the crew and their worktrees go by the same rule; a member whose worktree was removed gets it back, from its branch, on its next turn after you unarchive it; the dialog lists which it expects to remove and which to keep, and the archive result lists what it did. Archiving never deletes branches, pull requests, or conversation history, and a retired crew's brief and roster stay readable in the **Retired crews** section of Fleet, which lists retired crews from every project.

Persona instructions describe intended behavior. They do not grant permissions or guarantee that an agent obeys them. The displayed access level reflects supported provider controls; unsupported modes appear as **Blocked**. A persona whose access level your app doesn't recognize, because the environment runs a newer J5 Code, appears as **Unsupported** with the policy's name and can't be launched, edited, or duplicated from that app until you update it.

### Library sources

The **Library sources** section below the persona list shows the folders the selected environment reads YAML definitions from, whether each folder exists, and how many definition files it holds. Folders are read recursively, so you can point the library at the top of a shared repository and every persona YAML in its subfolders is included, the same way **Import → Folder** works. Choose **Add folder** to browse the environment's own filesystem (not your device's) and pick a folder; you can also type or paste a path in the picker. To remove a folder, choose **Stop reading folder** from its **⋯** menu on web and desktop, or use its trash icon on mobile. Changes are saved to that environment's folder configuration and take effect on the next catalog read. The default source is the `personas` folder under the environment's state directory. If it does not exist, it contributes no personas and its row reads **Default · not created**. Created and imported personas remain available even without a source folder.

When a folder lives in a git checkout, the row notes uncommitted changes in that folder and how many commits the remote is ahead. T3 Code only reads git status; commit, push, and pull with your usual tools. On web and desktop, **Open in editor** in the folder's **⋯** menu opens the folder in your preferred editor when one is available on that environment.

### Older tasks

Tasks that ran before personas stopped owing a file keep the handoff status they recorded. The persona control and, on web and desktop, the persona chip beside a delegated child's Lineage row and subagent card still show it, and on web and desktop the chip opens the file in the Artifacts page. Nothing updates that status, and runs started since never get one.

If a source file is invalid, the remaining personas stay available. Settings → Agent Setup reports the file path and reason so you can fix it in your editor. The next catalog read picks up the correction.

The persona library is separate from the Lineage section and subagent cards, which show runtime activity.

For environment setup, see [Configure a persona library](../runbooks/persona-library.md).
