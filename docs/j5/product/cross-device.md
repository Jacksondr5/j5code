# Cross-device

## Problem

A person's fleet does not live on one machine. Work agents run on a work server that only the work network can reach; personal agents run at home; a laptop is the client for both. The person wants one inbox and one Fleet page, not one per machine — and eventually wants an agent on one server to be able to ask an agent on another. The prior-art platform tried to replicate identity across machines, never built the transport, and rejected deliveries that were not local ([problems](problems.md): fleet observability, human attention).

## Definition

State can do exactly three things across machines: **authority can replicate, messages can cross, or views can merge.** J5's position is that **authority never replicates.** Messages cross — an Exchange can be delivered from one server to another — and views merge in the client. This avoids replicated identity and multi-master state entirely, and it was built into the communication protocol from the start: delivery is log-first, and a message that crosses projects is two writes, never one transaction, because collapsing them would assume a single host.

The four capabilities, and what each is:

| Capability                                        | Position                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Exchanges between agents on different servers** | Fits the protocol as designed: the delivery pipeline gains a peer step, and the receiving server writes its own received row. What is new is **peering** — the mutual record of which servers may talk, how messages travel between them, and with what credential — defined below. Nothing about addressing changes: an agent names a participant, and the platform knows which server it lives on. |
| **One ledger spanning servers**                   | **A permanent non-goal.** It would require replicated authority or remote execution. A project, its agents and its ledger live entirely on one server; an agent that needs a particular machine runs in a project on that machine, and agents exchange across servers.                                                                                                                               |
| **Merged inbox and Fleet page**                   | **The highest-value, nearest capability, needing nothing server-to-server**: the client already connects to every saved environment at once, and each server's reads merge in the client. Answers route to the server they came from. An unreachable server renders its last-known state with a staleness clock, never as empty and never as fine.                                                   |
| **Any other synchronization**                     | Deliberately none. Worktrees, provider credentials, settings, schedules, cost meters stay server-local by design; views merge their readouts. Role and Crew definitions travel as files. Refusing to sync is the feature.                                                                                                                                                                            |

### Environment links

A person connects two of their servers once. What they set up, see and remove is an **environment link**, called a link wherever a person or an agent reads it. (The link that brings a person in is a different thing, defined in [People and access](features/people-and-access.md).) A link between two J5 servers has two parts:

- **Messages.** Agents on the two servers message each other, in both directions. This part is **peering**, defined below.
- **Actions.** Each direction has a **level**, which says what agents on one server may do on the other. **Messages only** allows nothing more. The other levels are upstream's, from Read only to Full access, and let agents use upstream's tools on the other server and start work there. This part is upstream's linked environment, one for each direction above Messages only (see "Starting work on another machine").

The two parts are separate underneath, each with its own records, credential and lifetime, because one is J5's and the other is upstream's. That is a fact about who owns the code, and a person never meets it: they do not choose between the parts, set them up in two places, or remove them one at a time.

**Linking is choose, check, then link.** It is done from a web or desktop client that can manage access on both servers, in Settings → Environments, and the client offers it when the person adds an environment, if they can manage that server and at least one other. The person picks the servers to link with and one level for each direction. The two levels apply to every server picked unless one is given its own, and both start at Supervised, as upstream's link does. The client then checks every pair together: which server can reach which, and how each is run. One check settles both parts, because **actions take the route messages take**. A server that sends its messages to the other directly makes its calls there at the same address, and a server that stores messages for a poller reaches it through the line the poller holds (below). The client says, for each pair, how messages will travel and whether each direction's actions can be made, and asks only what the check could not settle. It then links each pair on its own, so one that fails says why and the rest are linked.

**What a level allows.** An agent never gets more on the other server than its own mode on this one, whatever the level. Below Full access, upstream holds the work a link starts to that link's own threads, so starting a Peer Agent on the other server needs Full access. Upstream ships linked environments as a setting that is off on each server; choosing a level above Messages only turns it on for the servers involved, and the client says so.

**A link over time.** Each pair is one row in Settings → Environments. A direction's level can be changed there at any time, in one step. Raising it from Messages only adds that direction's actions, whether the pair was linked that way a minute ago or peered long before links existed: the route is the one its messages already take, so nothing is checked again, removed or set up afresh. Setting it to Messages only ends that direction's actions and nothing else. Upstream's links last 30 days. The row says when a pair's actions run out, and the person renews both directions there in one step, or from an agent's request in a thread. Nothing renews a link without a person, since upstream has a person approve it again. Messages do not run out with the actions. **Removing a link** ends both parts on both servers: the peering, with everything that wipes (below), and each direction's linked environment with the session it held.

**An agent can ask for a link.** Upstream's request card stays: the agent gives its reason, and the person picks the server and the level and approves. In J5, approving links the pair. That sets up messages, and actions in the one direction the agent asked for; the other direction stays as it was, or at Messages only on a new link. On a pair that is already linked, the card raises that direction's level or renews it. An agent has upstream's link tools only while its server has linked environments turned on, as upstream ships them, so the first link a server takes part in is made by the person.

**A link can have its actions part alone.** A link made from the command line, or with a server that runs T3 Code and not J5, is upstream's link and nothing more. For now, so is one made in the mobile client, which keeps upstream's link card and list. Such a pair's row says that actions work and messaging is not set up, and offers to set it up where the other server runs J5. A link is read from what the two servers hold, so pairs that were peered, linked or both before the link flow existed show in the same rows, as they are, with nothing made again.

### Peering

Peering is the messages part of a link. Two servers that may exchange messages are **peer servers** ("peer" alone, in the A2A definition, means another agent). Peering is pairwise and mutual: each server holds a **peer record** for the other — the peer server's environment id and name, how messages travel to and from it, the origin this server reaches it at when it connects to it, the credential the peer server issued for that and when it expires — and each server that is connected to sees the other as one more authorized session in Settings → Sharing & access, alongside paired devices and machine tokens, and revocable there like them. The set of a server's peer records is its **peer registry**. There is no directory of servers: a server knows only the peers it has been introduced to.

Messages travel between peer servers in one of two ways, chosen for each pair when it is linked:

- **Send directly.** Each server opens connections to the other and delivers to it. Each record's **link mode** is `push`.
- **Poll.** One server cannot be reached — a laptop behind an office firewall that drops every inbound connection — or may be off when a message arrives, such as a laptop that sleeps, so it opens every connection itself. The reachable server **stores** the messages for it until it **polls** for them, and it sends its own messages to the reachable server directly. The storing server's record of the poller has link mode `store` and no origin; the poller's record of the storing server has link mode `poll`.

A pair's way of travelling changes only by removing the link and linking again. The address a server reaches its peer server at changes in place: the server presents the credential it already holds at the new address and records the address once the same peer server answers there, so no credential changes and nothing waiting is cancelled. Removing a link removes the peer, and **removing a peer wipes the slate** on the server that removes it: any session the peer had there is revoked, every message still waiting to reach the peer is cancelled with a notice to its sender, and every open Exchange with a participant there is dropped with the usual notice. The removal is one write: a message from or for the peer that arrives meanwhile is wiped with the rest or, once the removal is done, refused. Linking again starts empty; nothing cancelled or dropped comes back.

A polling peer is **online** while it has polled within the last two minutes, and **offline** since its last poll after that; a poller polls at least every half-minute while it runs, so its polls are its heartbeat. A poll counts once it reaches the storing server, because a poll held there shows the poller is present. The same rule tells the poller whether the storing server is online, counting each poll the storing server starts to answer.

Servers do not find each other; **the client introduces them.** The client is the one party that is already connected to both environments, so linking is an act taken there. It first checks which way connections can go, by asking each server to reach the other at the addresses that server knows for itself, and how each server is run: one the desktop app runs, or one started by hand, may be off when a message arrives, and a message sent directly to a server that is off fails after a few quick retries. From that it recommends how messages travel in each direction, asks only what the check could not settle, and lets the person set it up differently. It then asks each server that will be connected to for a credential bound to the other server's identity, tells the connecting server where to reach it, and each connecting server confirms it can reach the other before it records the peer server; a storing server records its poller when the poller first presents the credential issued for it. The origin the client itself uses is a hint, not the answer — a loopback or forwarded address that works for the client may not work for a server — so the person confirms the origin to use.

**A server's name is its own.** Each server reports one name for itself, the one every client already shows for it, taken from its machine's name; a peer record carries the other server's current name, refreshed when they greet, poll, or read each other's address book, so agents and every client see the same name. Renaming a server means renaming its machine. Peer servers also state their protocol version on everything they send each other, each side checks the other's, and a server updated past the other's protocol stops exchanging with it and says which server to update, rather than misreading it.

**Agents see where participants live.** An agent addresses a participant by its id exactly as it does locally; the platform resolves the participant to the server it lives on — the sender's own or a peer server. Once a server has a peer, its address book names the server each participant lives on, and whether a peer server that polls this one is available; a send to a participant on a peer server names that server in its result, and the envelope of a message from one names the server it came from. People give their servers different capabilities — Xcode on a laptop, a database connection on a work server — and an agent that can see where each participant lives can pick the right one. No messaging verb takes, chooses or manages a server: where a participant lives is a fact the platform states, never one a message names, and which server can do what is the person's to tell their agents.

**A person stays server-local.** A person's participant, their asks, and their inbox belong to each server they use; an ask to a person is delivered on the sender's own server, and the person's view of several servers is the client's merge described above. Peering carries messages between agents, and nothing else.

Delivery across peer servers is the same delivery with one more step: the send is a ledger row on the sender's server, the peer server records its own received row, and that acknowledgement is the sender's delivery receipt. Across servers the receipt means the peer server accepted and recorded the message; delivering it into the agent's thread is then the peer server's own delivery, which retries and alarms there, attributed to the sender as any delivery is. Sent directly, failure to reach the peer server retries and alarms on the sender's server as any failure does. To a polling peer, the message is stored without retrying or alarming until the peer polls for it, and the poller's acknowledgement is the receipt. A message that alarms on the sender's server, one the peer server refuses, or one cancelled before it got there, is reported to its sender; once the peer server has returned the receipt, an alarm there is not reported back. Everything that flows back — a reply, a silence notice, a lifecycle closure — travels the same path in reverse, which is why peering is mutual: one Exchange needs both directions. Peer servers reach each other directly, or one polls the other over connections it opens; a relay or tunnel is never a required part of it.

Peering is also where another person's server attaches, when that time comes — person boundaries, what may cross, and trust live in the peer record, and nothing else in the architecture needs to anticipate other people.

History durability is **client-pulled backup**: each connected client periodically pulls a consistent snapshot from every server it connects to, so the client's existing always-connected fan-out is the backup fabric, with no new infrastructure. Its design — the snapshot endpoint, cadence, retention, restore — is later; the direction is settled.

What this never does: no replicated state, no multi-master, no moving a project's ledger between servers, no global agent registry (peering is pairwise), no messaging verb that chooses or manages a server, no dependence on a relay service (servers reach each other directly, by polling, or through a line one of them holds; a relay could later be one transport among others, never a required service).

### Starting work on another machine

Messages are not the only thing that crosses. The actions part of a link is upstream's **linked environment**, which lets an agent act on another machine: one server signs in to the other's MCP server as a client, and an agent names that machine to use upstream's tools there. A call through it is direct and synchronous, so it works only while the caller's server can reach the other machine; peering carries messages, which may wait for a machine that is asleep or polls. The mechanism, its tools, its access levels and its 30-day lifetime are upstream's, and J5 takes them as upstream ships them. What J5 changes is how a person sets one up on web and desktop, as part of a link ([divergence D47](upstream.md)). Linked environments are J5's way to start work on another machine:

- **A delegate there.** `delegate_task` aimed at a linked machine starts the delegate on that machine, as upstream does: the caller's server launches it there and follows it until its result comes back to the parent. A delegate on a J5 machine stays out of that machine's ledger, as every delegate does. A persona can be delegated there too, resolved from that machine's persona library against that machine's models; a plain delegate there runs only on a model that machine's Models for custom members allows.
- **A Peer Agent there.** `j5_spawn_agent` aimed at another J5 machine starts the Peer Agent on that machine, in a project there. The caller's server makes the call over the link and names the spawner, and the new agent gets the same first turn as a local spawn: who spawned it, on which server, and how to reply. The spawner is recorded on that machine the way an outside agent is: the new agent is a root of its project there, and archiving either one leaves the other alone. The caller gets the new agent's participant id and can message it at once. This needs both parts of the link: Full access towards that machine, to start the agent and to let it use J5's tools, and messages, so that the two can talk. A link with its actions part alone is refused.

Starting work this way needs the caller's server to reach the other machine, directly or through the line a polling server holds open (below). A machine that is asleep or off cannot be reached either way.

### A line to a server that cannot be reached

A server that polls another cannot be reached by it, so on its own a link from the storing server to its poller could never work, and the storing server could never start work there. So **a polling server holds a line**: while it runs, it keeps one connection open to the server it polls, and the storing server makes that connection available at an address on its own loopback. Anything on the storing server that calls that address is talking to the poller, so upstream's link from the storing server to the poller uses that address and works as it does over any other. Linking and starting work then go both ways between the two, and the line reaches the poller from the storing server only, never from anywhere else.

The line is opened with the credential the poller already polls with, so it needs no setup of its own and says which server it carries: choosing to poll is all it takes, and that is what linking offers when one server cannot reach the other. Its address stays the same for as long as the two are peered, so a link recorded with it keeps working from one line to the next. The person never sees or gives the address: linking the storing server to its poller uses it. It carries calls through links and nothing else: messages keep travelling by polling, because a poller that is asleep has no line, and a message must still wait for it.

When the line is down, because the poller is asleep, between networks or reconnecting, a call through it fails at once, as a call to any machine that does not answer does. A call through a link that the other machine does not answer fails with its own code, `peer_unreachable`, so an agent can tell an absent machine from a refusal. The platform never retries such a call, since one replayed later may no longer be wanted. Instead, a thread whose call to a server that holds a line failed that way is told once, when that line is next up, which of its calls failed there and when, and decides for itself what to do; a restart of this server before then forgets them. Upstream's follower of a delegate already running there keeps retrying on its own, so the delegate's parent needs no notice.

## Acceptance criteria

1. A project, its agents, and its ledger exist on exactly one server; nothing moves a ledger between servers.
2. Every person-facing surface that shows fleet state — the inbox, the Fleet page, notifications — merges every connected environment from day one, and each item names its environment.
3. An answer or action taken on a merged surface is routed to the server the item came from.
4. An unreachable server's items render with their last-known state and a staleness clock; they never disappear and never render as healthy.
5. Nothing that is server-local by design — worktrees, provider credentials, settings, schedules, cost meters — is synchronized between servers.
6. Server-to-server Exchange delivery goes through pairwise peering, and the receiving server records its own received row.

### Merged surfaces

7. Environment labels appear on merged items and choices only when the results span more than one environment; a single-environment client shows none.
8. A connection that can only read shows that environment's agents and asks and refuses to create, launch or answer there, with the control saying why.
9. A count over merged environments is marked incomplete when any environment could not be refreshed, and shows no number when none could be.
10. An environment whose server lacks the fleet features is reported as unsupported, never as empty.

### Peering

11. A server delivers to, and accepts deliveries from, only the servers in its peer registry; a peer record names the peer server's environment id, its name, and its link mode, and either the origin this server reaches it at with the credential the peer server issued and when it expires, or that the peer polls.
12. Peering is mutual: the client records each environment as the other's peer server in one introduction, and removing either side ends delivery in both directions. Removing a link is a clean break: a client that can manage both servers removes both sides at once, and one that can manage only this one warns that the other server keeps its side, with Cancel the default and "Remove here only" the deliberate choice. Removing a peer cancels every message still waiting to reach it, with a not-delivered notice to each sender, and drops every open Exchange with a participant on it, with the usual drop notice; linking again starts empty. Linking a server that still holds an old record of this one, such as one left by a removal made on this side only, clears that record first, or names the server to clear it on when this client cannot manage it. An introduction that fails partway stops and reports each step; it leaves any credential it issued unused and the other side's existing credential working, so a retry or a removal clears the half-recorded state.
13. A peer server's credential is an ordinary session of the issuing server, bound to the peer server's environment identity and to a scope that permits only accepting deliveries, polling for stored ones, holding a line and reading the address book; it appears in Settings → Sharing & access. It is long-lived rather than renewed, and the holder's record shows when it expires. When it is revoked, because the issuer removed the peer or its session was revoked, or it has expired, the holder's deliveries are refused and alarm with that reason, a holder that polls stops polling, the pair's row says on the holder's side that the other server ended messaging, in either link mode, with removing the link as what is left to do, the issuer's record shows the peer server without a live session, and the address book reports it as unread, never omitted.
14. A link's messages part is set up by linking (AC36–AC39), from a client connected to both environments with administrative scope. Before anything is recorded, the client checks which way connections can go and how each server is run, states how messages will travel in each direction, and asks only what the check could not settle; a failed check shows the error it got. The person confirms the origin to use, which may differ from the one the client uses; the server names come from the servers. The client offers a setup only when both servers support poll mode; when either does not, it names the server to update and offers nothing else, while an operator can still peer an older server to send directly from the command line.
15. A peer server that is sent to directly or polled is recorded only after the recording server has reached it at the stated origin with the credential it issued; an unreachable origin is refused with the reason, never recorded, and a known peer server is not moved to a new origin unless the person says so. Moving one keeps the credential this server holds for it, and records the new origin only once the peer server answers there to that credential; nothing waiting for it is cancelled and no Exchange is dropped. A polling peer is recorded by the storing server when it first presents the credential issued for it.
16. An agent addresses a participant homed on a peer server by the same participant id it would use locally, and no messaging verb takes, chooses or manages a server; once a server has a peer, the address book, send results and envelopes name the server a participant lives on.
17. The address book lists participants on peer servers beside local ones with their project's id and title. It reads the roster of each peer server it sends to directly live on each call, so an unreachable one costs the call its timeout and is reported as unread in the listing, never omitted silently. A polling peer's roster comes from the snapshot it last sent when it polled: current while it is online, "as of" that time while it is offline, and unread until its first poll.
18. A message to a participant on a peer server is recorded in the ledger of the sender's project before the call returns, for a participant the address book resolves or one this server has already exchanged messages with; a first message to a participant on a peer server that cannot be read is refused with the reason. The peer server records its own received row before delivering to the agent's thread, and that acknowledgement is the sender's delivery receipt: it means the peer server accepted the message, and delivery into the thread is the peer server's to retry and alarm on. Failure to reach a peer server sent to directly retries and alarms on the sender's server as any delivery does. A message to a polling peer is stored without retrying or alarming until the peer polls, and the poller's acknowledgement is the receipt; one the poller refuses is reported to its sender.
19. Retrying one message to a peer server, or handing it out again to a polling peer, never yields a second received row or a second delivery.
20. A reply, silence notice, withdrawal or lifecycle closure for an Exchange across peer servers travels the peer path back to the origin server and closes or notifies the origin Exchange exactly as a local one would; a withdrawal closes the Exchange without waking the answerer, locally or across servers.
21. A person is never addressed across peer servers: an ask to a person is delivered on the sender's own server.
22. Peer servers reach each other directly at the recorded origin, or one polls the other over connections it opens; no relay or tunnel is required for peering.
23. A delivery to a peer server carries the sender's display name; the receiving server keeps it with its received row so the client names a remote sender in the timeline as it names a local one, and no agent verb needs it.
24. Every request and answer between peer servers states the sender's peer protocol version, and each side checks the other's, so a mismatch is caught whichever server was updated; a server that states none counts as the first version. A mismatch is refused, naming which server to update, and shows on the peer record until a later exchange between them succeeds. Peer servers also state their capabilities when they greet each other, and a pairing that needs polling is refused before anything is recorded when the storing server lacks it.
25. A message waiting for a polling peer that is cancelled — because its sender was archived, for example — is withdrawn only if the peer has not yet been handed it; one already handed out stays deliverable and its acknowledgement records it delivered. Removing the peer cancels every waiting message, handed out or not. When an Exchange closes whose ask was cancelled before it was delivered or handed out, no closing notice goes to the peer server, which never held it.
26. A server tells its peers what it can do in every greeting, poll and roster answer, and a peer's record keeps the latest. A message sent with `steer` or `restart` crosses with that request and the sender's permission limit only to a peer that says it lands a message as asked; the receiving server refuses it for an agent that runs above the limit.

### Starting work on another machine

27. `delegate_task` aimed at a linked J5 machine starts the delegate there, follows it to its result and keeps it out of that machine's ledger; with a persona, the persona is resolved from that machine's library and models, and a plain delegate there is refused on a model that machine's Models for custom members does not allow.
28. `j5_spawn_agent` aimed at a J5 machine this server is linked to, with messages set up and Full access towards that machine, starts the Peer Agent in a project there, records the calling agent as its spawner with no placement parent, gives it the same first-turn facts as a local spawn naming the spawner's server, and returns its participant id; a message the caller sends it straight away is delivered. A retry with the same `client_request_id` never starts a second agent.
29. Starting work on another machine that the caller's server cannot reach, directly or through a line, fails with `peer_unreachable`, naming that machine; nothing is recorded as started.

### A line to a server that cannot be reached

30. A server that polls another holds a line to it while it runs, opened with the credential it polls with. The storing server gives each poller one address on its own loopback that stays the same while they are peered, and knows whether the line is up. Linking the storing server to its poller uses that address without the person seeing or giving it.
31. A call the storing server makes to a poller's line address reaches the poller's server as a direct call would, so upstream's link from the storing server to the poller, its setup included, works through it as through any address. Nothing outside the storing server reaches the poller through the line.
32. Messages between a poller and its storing server travel by polling whether or not the line is up.
33. While a line is down, a call to its address fails at once; the poller opens a new line as soon as it can, and the platform retries nothing the line carried.
34. A call through a link that the other machine does not answer, through a line or at any other address, fails with `peer_unreachable`, never with a code upstream's follower treats as final, so a delegate already running there is followed again once the machine answers.
35. A thread whose call to a server that holds a line failed with `peer_unreachable` gets one platform notice when that line is next up, naming the server and each tool it called there and when, unless this server restarts first. A delegate's follower is not such a call, and an archived thread, or one that takes no messages such as a delegated child, is not told.

### Environment links

36. Linking is done from a web or desktop client that can manage access on both servers. It starts from Settings → Environments, and the client offers it when the person adds an environment, if the client can manage that server and at least one other it is not yet linked with; the offer can be skipped. The person picks one or more servers to link with and a level for each direction; the two levels apply to every server picked unless one is given its own, and both start at Supervised.
37. The levels are Messages only and upstream's five access levels. The picker says that Full access is what starting Peer Agents on the other server, and acting on that server's own threads, need.
38. Before anything is recorded, the client checks every picked pair together and states, for each pair, how messages will travel in each direction (AC14) and whether each direction's actions can be made: at the address its messages are sent to directly, through the line of a server that polls, or not at all, with the reason. A pair the check settled asks nothing, and a pair it could not settle asks on its own row.
39. Linking a pair records the peering (AC12, AC15) and makes upstream's link for each direction above Messages only at the address AC38 stated, with no address or pairing code typed. A pair that fails reports each step and leaves the other pairs linked, and a direction whose actions cannot be made is left at Messages only with the reason on its row.
40. Choosing a level above Messages only turns on upstream's Linked environments setting on each server of the pair where it is off, and the client names those servers before it links.
41. Settings → Environments lists links in one section, one row for each pair among the servers this client manages, and no other section lists peer servers. A row shows what a peer record shows, how messages travel and what is wrong on either side, with each direction's level and when the pair's actions run out.
42. A direction's level is changed on its row, in one step and with nothing else asked. Raising it from Messages only makes that direction's link at the address its messages already take, with no new check of the pair, and turns on upstream's Linked environments setting as AC40 says; if the other server does not answer then, nothing is recorded and the row says why. A change between upstream's levels links that direction again at the new level. Setting it to Messages only forgets that direction's link and revokes its session on the other server. Messages, and anything waiting between the two servers, are unaffected by any of these.
43. A pair's actions are renewed from its row in one step that covers both directions, with no pairing code typed when the client manages both servers. Nothing renews a link without a person, and messages keep travelling after actions have run out.
44. Removing a link ends both parts on both servers: each peer record, with what AC12 cancels and drops, each direction's link, and the session each one held on the other server. The confirmation says what is lost, including delegates on the other server that are no longer followed. A client that manages only one server warns as AC12 says, and "Remove here only" removes this server's peer record and link and revokes the other server's sessions here.
45. An agent has `t3_environment_link` only while its server has upstream's Linked environments setting on, as upstream ships it. Its request shows upstream's card with the agent's reason. The person picks a server this client manages and the level for this server's agents on that one, sees the check's result for that direction, and approves. Approving links the pair as AC39 does, with the other direction left as it was, or at Messages only on a new link, and the agent is told as upstream tells it. On a pair that is already linked, the card raises that direction's level or renews it. The card takes no address or pairing code: a server this client does not manage is named, with adding it to this client as the step to take.
46. A pair that has upstream's link and no peering is a row in the same list that says actions work and messaging is not set up, with setting it up offered when the client manages both servers and the other runs J5. That is how a link looks when it was made with `j5 environment link`, with a server that runs T3 Code, or, for now, in the mobile client. A server that runs T3 Code can be picked when linking: it is linked for actions only, as upstream links it, and its row says messaging needs J5 Code there. `j5 a2a peer` still peers two servers from the command line, and that pair is a row with both directions at Messages only.
47. Pairs that were peered, linked or both before the link flow existed are rows in the state their records are in. Nothing is migrated, issued again or asked on first run, and such a row is changed like any other: a pair that was only peered gains actions when a level is raised on its row (AC42).
48. An agent's `t3_environment_unlink` forgets this server's link to the other, as upstream does. Messages are unaffected, and the pair's row shows that direction at Messages only.

## Scenarios

- **Two servers, one inbox.** The user's client connects to the work server and the home server. An ask from an agent in Billing Migration (work) and one from an agent in Support Rotation (home) appear in one inbox, each tagged with its environment; answering each reaches the right server. (AC2, AC3)
- **A server goes dark.** The home server is asleep; its rows stay on the Fleet page with "as of 40m ago" and never vanish. (AC4)
- **One server is read-only.** The user's connection to the home server has no operate scope: its agents and asks appear in the merged lists, and the answer box for a home-server ask explains that this connection cannot reply. (AC8)
- **Linking two servers.** The user opens Settings → Environments on their laptop, connected to the work server and the home server, and links them, leaving both levels at Supervised. The check finds that each can reach the other and that both run as always-on services, so the dialog says each sends to the other directly, at the addresses it proved, that actions work in both directions at those addresses, and that Linked environments will be turned on for both; it asks nothing. Each server confirms it can reach the other at the origin the user confirmed, and the pair becomes one row: messages sent directly, Supervised each way, actions running out in 30 days. Had the home server been run by the desktop app, the dialog would have asked how the work server should get messages to it, with storing them until the home server polls as the default. Removing the link later removes it on both servers when the client can manage both, or says which server still lists the other when it cannot. (AC11–AC15, AC36–AC41, AC44)
- **A third machine.** The user adds their Mac server to the same client with a pairing link that manages access. When it is added, the client offers to link it, with the work server and the home server ticked. The user sets "agents on the Mac server may, on these" to Messages only, keeps the other direction at Supervised, and raises the work server's row to Full access, since agents there will start Peer Agents on the Mac. Both pairs are checked at once and linked together. (AC36–AC39)
- **Adding actions to a pair that only messages.** The home server and the user's old desktop server were peered before links existed, so their row shows messages sent directly and Messages only each way. The user raises "agents on the home server may, on the desktop server" to Supervised on the row. The client says Linked environments will be turned on for both and makes the link at the address the home server already sends its messages to. Nothing is checked again or removed, and the messages waiting between them are untouched. (AC40, AC42, AC47)
- **An agent asks for a link.** An agent in Billing Migration, on the work server, is asked to delegate an iOS build to the Mac server, which is not linked. The work server has Linked environments on, from its link with the home server, so the agent has the link tools. It raises a link request with its reason. The user picks the Mac server and Supervised on the card, sees that the work server can reach it, and approves. The two are linked: their agents can message each other, the work server's agents can act on the Mac server at Supervised, and the Mac server's agents can do nothing on the work server. The agent is told and delegates the build. A month later the same delegation is refused because the link's actions have run out; the agent raises the card again, and approving it renews them. (AC43, AC45)
- **A link approved on the phone.** The user approves an agent's link request from the mobile client, which shows upstream's card. The link has its actions part alone. Back at their desk, the pair's row says that actions work and messaging is not set up; the user sets it up there, and the row becomes an ordinary link. Until then, starting a Peer Agent on that machine is refused. (AC28, AC46)
- **The agent on the Mac.** The user's Mac server has Xcode and the work server does not, and the user's instructions to their agents say so. An agent in Billing Migration, on the work server, needs an iOS build; its address book lists the agents homed on the Mac server beside local ones, each naming the Mac server, so it picks one there and asks it for the build by participant id, as it would ask any participant. The ask is recorded in Billing Migration's ledger, the Mac server records its received row and delivers it, and the reply travels back and closes the Exchange, its envelope naming the Mac server. The agent saw where the other agent lives and never named a server. (AC1, AC6, AC16, AC18, AC20)
- **The home server is asleep.** The home server runs in the desktop app and polls the work server. An agent on the work server asks an agent homed on the home server while the home server's lid is closed. The send is recorded and stored, and its result says the home server is offline and when it was last available; the work server's address book lists the home server's agents as of its last poll. Nothing retries or alarms. When the home server wakes, it polls, receives the ask and acknowledges it, and the reply comes back directly. A first message to an agent the home server had never listed when it last polled is refused, naming that as the reason. Had the two servers been linked to send directly, delivery would retry and then alarm on the asker, and the address book would report the home server as unread. (AC17, AC18)
- **A laptop behind an office firewall.** The user's work laptop sits behind a firewall that drops every inbound connection, and its work server is always up. Linking them from the laptop, the check finds the work server cannot reach the laptop, so the dialog says the laptop sends messages to the work server directly, and the work server stores messages for the laptop until the laptop polls for them; it asks nothing. The work server records the laptop when the laptop first presents its credential. From then on the laptop opens every connection: an agent on the work server that asks an agent on the laptop has its ask stored and picked up within seconds while the laptop is awake, and an archive on the laptop reaches the work server's address book on its next poll. When the work server's agent messages an agent the laptop archived after its last poll, the laptop refuses it when it polls and the sender gets a not-delivered notice. (AC14, AC15, AC17, AC18, AC22)
- **Starting work on the laptop from the work server.** The same laptop polls the work server, so while it runs it also holds a line there. When the user linked the two, the check said that the laptop's actions reach the work server directly and that the work server's reach the laptop through its line, while the laptop runs; the user never saw the line's address. An agent on the work server then delegates an iOS build to the laptop; the delegate starts there through the line, and its result comes back to the agent. That evening the laptop sleeps mid-build: the delegate's follower keeps retrying on its own, and another agent's attempt to start a second build there fails with `peer_unreachable`. When the laptop wakes and its line is up again, the first build's result arrives once the follower reaches it, and the second agent gets one notice naming the laptop and the call that failed, and decides whether to try again. Messages between the two kept travelling by polling throughout. (AC28–AC35)
