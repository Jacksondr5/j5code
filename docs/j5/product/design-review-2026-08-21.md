# Design review 2026-08-21 — settled register

A full-design grilling session (Jackson + Product, 2026-08-21): every open branch of the design tree visited round-by-round until the frontier was empty. This register holds the rulings; the three principles adopted in the same session live at `principles.md`. Nothing here reopens D1–D10, E1–E6, or X1–X5 — these rulings compose with them. One row per decision, all SETTLED 2026-08-21.

## The register

| ID  | Area                    | Ruling                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | Exchanges / lifecycle   | **Archiving a participant terminates its obligations loudly.** Archive appends a platform-authored terminal notice per open inbound exchange (`receiver-retired`, mapped to Dropped, carries do-not-retry), delivered to each waiter through the normal pipeline. Sender-side open outbound exchanges get the same retirement disposition. No exchange ever waits forever on a node that can no longer answer.                                                                                                                                    |
| R2  | Squadron / lifecycle    | **Squadron archive is user-only, loud, and evented.** It force-closes the squadron's open exchanges via the R1 mechanism (notices reach cross-squadron waiters); human-inbox rows from the squadron leave with a visible record, never silently.                                                                                                                                                                                                                                                                                                  |
| R3  | Exchanges / closure     | **The sender judges completeness, prompted at closure.** When a reply lands, the reply-delivery envelope (third rendering of the one formatter) states: this reply closed the exchange entirely; if anything you asked remains unanswered, open a new exchange — nothing else is tracked. Completeness is a judgment call and therefore never code's (Principle 3).                                                                                                                                                                               |
| R4  | Silence / notices       | **Notices record facts; projections assign labels.** `silence.notice` carries the full measured bundle — turn ended, no closing reply, every open outbound exchange listed structurally (generalizing D6's structural peer id). Which single state labels an edge (awaiting-human vs blocked-on-peer vs turn-ended) is projection/display policy: disposable, tunable without ledger migration. States are evaluated at the recipient's turn-end over durable ledger facts regardless of which turn created them.                                 |
| R5  | Dashboard / inbox       | **Two features, not one.** The inbox is pure: letters agents deliberately sent to the human — no inferred mail, no auto-promoted stalls. The observability dashboard is where the human investigates "why isn't X done": it highlights e.g. an IC blocked-on-peer for 2 hours with the peer idle, prompting a nudge to whichever agent coordinates X. They may share a UI, never a data model.                                                                                                                                                    |
| R6  | Ledger / triggers       | **Machine triggers are recorded roots, not participants.** Schedule/check fires append a ledger event (`trigger.fired`-kind: source id + run id) so machine-initiated chains have a recorded origin in playback. Triggers mint no exchanges and emit no silence; participant = has a thread, unchanged. External-systems-as-nodes stays an open door.                                                                                                                                                                                             |
| R7  | Cost                    | **Cost rolls up squadron → agent, nothing between.** Cost is measured per agent; the squadron is the only aggregation (membership immutable, so accounting is stable). No org-subtree or sub-squadron cost accounting — the re-parent attribution problem is thereby deleted, not solved.                                                                                                                                                                                                                                                         |
| R8  | Identity (item 3 seed)  | **Identity = git-versioned definition files; no memory in the bundle (v1).** Closes the 2026-08-14 open counter in favor of the original no-new-memory-store call: portability comes from git (per X-register direction); provider memory is accepted as non-portable local seasoning; what an agent must never forget belongs in its definition. The Role/manifest system (item 3) carries this fully.                                                                                                                                           |
| R9  | Human identity          | **Durable local person id from day one.** The ledger needs a _stable_ id, not an _authenticated_ one: mint `human:<id>` at first run, use it in every row and envelope. External auth (e.g. Clerk) binds to it later at the peer registry — X4's designated cross-person seam. App login stays deferred.                                                                                                                                                                                                                                          |
| R10 | Exchanges / linkage     | **Optional `regarding: exchange_id` on open.** A follow-on exchange (R3 reopen) links to the exchange it survives; envelope tells reopeners to carry it. One nullable column now vs a migration later. Guardrail noted with it: simple tools over completeness-striving — we are pushing the bounds of how AI works; this field passed only because it is one field.                                                                                                                                                                              |
| R11 | Ledger / retention      | **Archived ledgers are readable forever.** Archive removes a squadron from active views only; its ledger stays immutable and readable indefinitely; playback works forever; X5 client-pulled backups include archived ledgers. No deletion story in v1.                                                                                                                                                                                                                                                                                           |
| R12 | Crews / concept         | **Two concepts: the manifest (definition) and the crew (instance).** The platform ships the machinery — author, spawn, render; every playbook (e.g. Jackson's PR Group) is one user-authored manifest, never the product's opinion. Manifests are git-versioned files (same mechanism as R8 identity).                                                                                                                                                                                                                                            |
| R13 | Naming                  | **Fleet / Squadron / Crew, definition = Manifest — the nautical-civil family.** A fleet is all vessels; a squadron is a detachment grouped under a shared purpose; a crew is the hands running one vessel, each with a named station; a manifest lists a crew's roles. Simple enough to teach at onboarding. Crew is the least military word in the family (film/pit/flight/road crew) and is role-native. "Team" is retired as a reserved term.                                                                                                  |
| R14 | Crews / lifecycle       | **Crews archive as a unit; members are never individually archived or replaced.** Rationale: agent death is usually recoverable (message them again), and an irrecoverably poisoned member has likely contaminated its crewmates. Recovery = respawn the crew from the manifest. Continuity is cheap because work lives in durable artifacts outside the agents (worktree, branch, PR): the successor crew picks up where the old one left off. Solo agents (no crew) stay individually archivable.                                               |
| R15 | Crews / workspace       | **Archive never destroys work.** Archiving a crew (or any agent) never deletes worktrees, branches, or checkpoints by default; workspace cleanup is a separate explicit act. (Broader management of durable items outside the platform: deferred to those systems' build-time.)                                                                                                                                                                                                                                                                   |
| R16 | Crews / spawn           | **Agents can spawn crews** (within their own squadron, from user-provided manifests) — a deliberate, recorded asymmetry with user-only squadron creation (E4). The middle-management thesis requires it.                                                                                                                                                                                                                                                                                                                                          |
| R17 | Crews / boundaries      | **A crew lives entirely inside one squadron; a crew renders as one org node** with members beneath it, so cascade operations (D10) treat it as a unit. Membership is fixed at spawn (composes with R14) — an agent is in exactly one crew by construction; counterpart references resolve once at spawn to agent ids (no seat indirection needed).                                                                                                                                                                                                |
| R18 | Captain / concept       | **Captain is a derived status, not a platform entity or a fourth tier.** The hierarchy is arbitrary-depth (managers of managers), so the management layer is made of agents in the placement tree, not container objects. A captain is any agent with crews placed under it — measured, never asserted. UI: captain chip + crews rendered as collapsible groups under their captain. ("Flotilla" reserved if a true container need ever materializes; none is expected.)                                                                          |
| R19 | Captain / rights        | **A captain may archive crews placed directly under it** — the only agent-invocable archive. Symmetric with R16 (retire what you command); safe because it triggers the same loud platform machinery (R1/R2). Not grandchild crews (route through the child captain or the human), not individual members (R14), not solo child agents (no identified need).                                                                                                                                                                                      |
| R20 | Crews / constraint      | **Crew members cannot spawn crews — enforced in the tool surface**, not by convention: the spawn-crew tool refuses callers holding a crew seat, with an error naming the next command ("escalate to your captain"). Crews are leaf teams; wanting more hands is an escalation.                                                                                                                                                                                                                                                                    |
| R21 | Hierarchy (amends D10)  | **Placement parameter deleted; "you command what you brief."** Spawn-time placement (sibling/other-parent/new-root) is removed: placement = spawner, always. The scenario that motivated it — spawning-and-briefing a crew for someone else — is ratified as an anti-pattern (proxy management; Principle 1): the decider sends decision + brief to the future captain, who spawns its own crew. Provenance stays separately and immutably recorded; human-only re-parent survives as the sole divergence mechanism; captaincy follows placement. |
| R22 | Communication invariant | **Any participant may message any participant; captains are never routers.** No permission check may ever enforce communication routing or spectrum position (Principles 1–2). The graph, not the hierarchy, is how you see through a middle manager.                                                                                                                                                                                                                                                                                             |
| R23 | Principles              | **Three principles adopted as named product docs** (`principles.md`): peer communication / hierarchical decisions; the human-contact spectrum (with riders: manifests declare posture; chattiness is measured — item 4; density lens directional); prompting-vs-platform elevated from the 2026-08-16 boundary ruling.                                                                                                                                                                                                                            |

## Foundations round (2026-08-22) — R24–R35

The session continued with a step back to foundations: Jackson's problem statement and goals, now captured in `problems.md` (the doc these rulings assume). Principles 4–5 were adopted in this round (`principles.md`).

| ID  | Area               | Ruling                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R24 | Principle          | **Status is read, never asked** — adopted as Principle 4. If the user must ask an agent for a fact, the platform is missing a surface.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| R25 | Envelopes / time   | **The platform stamps measured time facts into everything it delivers** — open-durations, delivery timestamps, elapsed-since-request — because agents are time-blind. Versioned envelope config, M2-adjacent. Expected to convert into proactive behavior ("it's been 8 hours, let me check"; "it _is_ tomorrow, let me raise it") — behavior to study and tune, not assume.                                                                                                                                                                                                                                                           |
| R26 | Attention model    | **Inbox ≠ backlog.** The inbox is an obligation queue: every item blocks a sender, demands a reply, scales with working agents. A backlog is non-blocking and may grow freely. Deferred items must never route through the inbox (an inbox with 100 items hurts the attention problem); a separate primitive is required — the memo (R31–R35). Amends R5's surface list: inbox / observability views / backlog pane — shared UI allowed, shared data model never.                                                                                                                                                                      |
| R27 | Playbooks          | **The playbook engine is platform; the steps are content** (brief-container precedent). Rulings: (a) the agent advances the step pointer by tool call — "on step 3" is a measured fact of the call with visible asserted-by provenance, never output-parsing; (b) linear sequences first, the initiative-level milestone/DAG view is the same primitive one level up — one family, linear ships first; (c) skills-per-step parked, unproven. New backlog candidate "playbooks & progress" — feeds item 4's panes, is not item 4. This is how PR Group and monitoring playbooks become expressible without being codified.              |
| R28 | Manifests          | **Platform schema, file storage.** Machine-read fields (model, reasoning effort, skill allow-list, posture, playbook ref) wrap the prose role text; the platform enforces mechanics because it reads them. Riders: it is the _user's_ content — portability and shareability are requirements; git currently solves both; the implementation must not un-solve them. Skill gating is platform-only work.                                                                                                                                                                                                                               |
| R29 | Shared squadrons   | **A distinct third capability** — not cross-device (X1–X5), not federation (X4 joins two servers; this is several people on one server, the L2-support vision: shift handoff without context transfer, two humans in front of one agent). Settled now: the **multi-human invariant** — nothing built from here on may assume exactly one human; every human-facing surface is person-scoped (R9 person ids). Delivery targets are **one user or all users** — no human group management on a single server. Duty-addressing ("the on-call") recorded as an open door, undesigned. Deep architecture session required before any build. |
| R30 | Agent primitives   | **Agent-provisionable cron/DB parked with a named trigger**: revisit when cross-machine sync or repeated agent-setup pain makes hand-rolled stores hurt. The monitoring fleet's scraper and incident DB stay outside the platform. (Platform-owned durable schedules remain settled-build, unchanged.)                                                                                                                                                                                                                                                                                                                                 |
| R31 | Memos              | **No per-turn injection** — that would trade forgotten notes for context rot; the back-burner is a feature. The platform's leverage (Principle 5): the tool's existence makes usage likely; the UI makes lapses visible — dashboard backlog view, badge on agents whose backlog needs working, a warning when archiving an agent with open memos, a chat drawer for picking the next topic.                                                                                                                                                                                                                                            |
| R32 | Memos / deferral   | **`resurface_after` is the one platform-initiated re-injection** — "page me after this time." Before the time the memo truly rests; after it, it returns stamped with R25 time facts. This field is what distinguishes a deferral from a backlog item.                                                                                                                                                                                                                                                                                                                                                                                 |
| R33 | Memos / visibility | **All memos are visible to the user — no private memos.** The backlog pane is pull-based (no clutter concern; the user arrives with attention to spare) and steering requires seeing everything the agent intends. Promotion to a real exchange is a deliberate agent act, never automatic.                                                                                                                                                                                                                                                                                                                                            |
| R34 | Memos / scope      | **Shaped, not generic — memos are the v1 agent data primitive.** Clear access patterns (append, list-open, resolve, defer) earn the store its place; a generic agent DB waits for R30's trigger.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| R35 | Memos / boundaries | Per-agent ownership (no crew-shared memos until a need shows); the owning agent resolves or drops its own memos, evented; the human sees all and nudges via normal messages. Name: **memo** ("slate" runner-up).                                                                                                                                                                                                                                                                                                                                                                                                                       |
