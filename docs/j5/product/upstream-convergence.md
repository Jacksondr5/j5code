# Upstream convergence watchlist

Where upstream T3 Code is building toward the areas J5 owns. Each entry says what upstream has, where J5 stands, and what would make us adopt upstream's version or change our own. Rewrite this file at every upstream advance (see [Merging upstream](../process/upstream-merge.md)); the line below names the upstream release it was last checked against.

Checked against `pingdotgg/t3code` stable `v0.1.7` @ `322f6544df` (1,466 commits past `v0.1.3` @ `d2c440312e`). Open pull requests read on 2026-11-04.

## Agent-to-agent messaging and control

- **Upstream:** the orchestrator MCP toolkit can send into another thread, wait on it, interrupt it and launch threads (`t3_thread_send`, `t3_thread_wait`, `t3_thread_interrupt`, `t3_thread_launch`, `create_threads`), answer another thread's questions (`t3_pending_request`) and reconfigure it (`t3_thread_configure`). Every tool declares who may call it. An agent outside the app can sign in with OAuth. Messages from agents carry `senderThreadId`, fold into one-line rows, and show their sender while queued too. A delegated child's question wakes its parent, steering into the running turn when the provider can steer without interrupting tools and otherwise queueing. A person can answer a delegated child's approvals from the parent thread on web, desktop and mobile; a child's questions no longer flag the parent. `t3_pending_request` still cannot approve a permission request; the change that let it was reverted and has not returned.
- **Linked environments** (new, a Labs beta, off by default, on each machine): two servers link over any route that reaches them, and an agent then names another machine's `environmentId` on thread, project and queue tools, or delegates there. Work a link starts is fenced to that link below full access. `t3_thread_launch` takes `clientRequestId` so a retry is safe. Agents can propose a link with a card, and `@` mentions a machine. Tool calls over a link need a direct connection, and upstream plans no poll mode. Import, handoff and "Continue on…" are [still open](https://github.com/pingdotgg/t3code/pull/16731).
- **J5:** a ledger for each project, addressable participants, Exchanges, Inbox and delivery receipts. J5 follows upstream's access model and outside-agent sign-in ([divergence D2](upstream.md)). It hides upstream's send and bulk-create tools, admits wait and interrupt (interrupt with J5's Captain rule, in place of `j5_stop_agent`), admits upstream's link tools as shipped, and admits launch only for link sessions, so a delegate another machine sends here can run, held to this machine's models for custom members ([divergence D42](upstream.md)). An agent in a side chat is refused J5 messaging, as a subagent is. A Crew seat asks its Captain. Native questions on J5-spawned Peer Agents or live seats notify their placement parent by queueing, and reach the Inbox as links; delegated children keep upstream's reactor and its approval roll-up. Pending-request answers follow upstream's checks. J5 peering stays the ledger's path between servers and sits beside linked environments in Settings → Connections. Peering polls for messages, which are not expected to answer at once, so a sleeping or firewalled machine still gets them later; tool calls are expected to answer at once and use the link's direct connection, so starting new work on a sleeping or firewalled machine fails visibly.
- **Watch for:** reply or ask semantics, an inbox, or responder attribution upstream. Child question or approval routing extended to threads an agent started that aren't delegated children; J5's Crew-seat question rule and Exchanges could then sit on top of it. An outside client that can _receive_ messages. Approval answering by agents returning. Upstream's [handoff layers](https://github.com/pingdotgg/t3code/pull/16751) landing, which would overlap J5's delivery across servers and is the moment to reconsider peering. A poll mode for links, which would change where peering and links split. Delivery so far is idempotent launches and retried notices, not receipts; receipts would be the signal to rethink.

## Launch, workspaces and parallel agents

- **Upstream:** workspace-aware launches, configurable branch names, tracked worktree setup. A "No project" project, which a thread can now turn into a real project where it stands. Multi-model send. `delegate_task` can give a child its own worktree, and can run on a linked environment. Providers can be switched per project. Projects can be pinned and archived. Storage cleanup removes settled threads' worktrees, including a finished child's once its parent settles. Threads can carry tags; tags have no UI or MCP tool and only hide threads while recording. Side chats (`/side`, `/btw`) are hidden forks with their own composer in the right panel, deleted with their parent or when closed unused.
- **J5:** `j5_spawn_agent` and Crews create Peer Agents with briefs; every one names its workspace, prepared through upstream's ThreadLaunch when it is new. `j5_spawn_agent` can start a Peer Agent on another J5 machine, over a link. J5 doesn't give agents `t3_thread_launch` or `create_threads`. `delegate_task` takes upstream's worktree option as shipped. Multi-model send is refused from a persona draft. Side chats are treated as subagents are: not participants, left out of the Fleet page and J5's analytics, and in their parent thread's scope, so whoever can see the parent can open them and whoever can write to it may delete them. A thread turned into a project keeps its participant where it was until J5 re-homes it.
- **Watch for:** coordination of fanned-out threads, or tags gaining a UI or an MCP tool, either of which comes close to Crews. Delegated children listed in the sidebar or Cmd+K: a delegated child with its own worktree and composer is already a Peer Agent in all but discoverability. Remote launch and delegation leaving the Labs beta, which would meet `j5_spawn_agent` on a peer server.

## Lineage, subagents and fleet views

- **Upstream:** a thread-details panel with Lineage (including remote delegates, Claude workflows by phase and a separate Side chats section), hover cards, per-turn subagent cards, a breadcrumb to the parent. `thread.stop` interrupts the turn, holds the queue, ends pull-request watches and stops delegated children. Every interrupt is bounded; a provider that ignores Stop shows "Agent not responding" with Force stop, which is a person's action and not an MCP tool. The sidebar's Waiting covers a thread blocked on another thread, and any pending question moves a thread to Input. OpenTelemetry export carries run and resource metrics. Upstream's copy calls the sidebar's active section "the inbox", which is not J5's Inbox.
- **J5:** placement and provenance, the Fleet page, sidebar spawned-children and Crew chips, persona identity on rows. Upstream's Lineage shows none of J5's relationships. `t3_thread_interrupt` with `stop: true` and Crew stop send `thread.stop`.
- **Watch for:** cross-thread grouping beyond one thread family, or an attention queue across threads. A view of run metrics in the app, which would come close to the Fleet page. [Sorting the sidebar shelf as a queue](https://github.com/pingdotgg/t3code/pull/26380) is open and is the nearest thing.

## Handoffs and history transfer

Two different things share the word "handoff". J5 docs call upstream's history transfer a **context handoff** and J5's persona document a **handoff artifact**.

- **Upstream:** context handoffs move a budgeted slice of history into a new provider conversation on a model or provider switch, a fork, or a portable restart. A failed native resume falls back to a fresh conversation without telling the person, except that a Codex thread another client is writing to now fails with a message naming that client; a resume whose handoff fits only a fresh conversation starts fresh, also without telling the person. A fork of a running thread always uses portable context.
- **J5:** persona handoff artifacts under `handoffs/`, with a nudge worker and a composer chip. The native-resume patch refuses a silent context handoff: a failed resume starts fresh only when the conversation is gone or an earlier delivery is uncertain, a resume whose handoff doesn't fit starts fresh as upstream's does, and each says so in its own words ([divergence D6](upstream.md)); upstream's writer-lock failure runs first.
- **Watch for:** upstream starting fresh only when the provider reports the conversation gone, and telling the person. That retires D6. The [visible divider](https://github.com/pingdotgg/t3code/pull/28195) is open; when it lands, decide whether a visible fresh start is enough.

## Steering and queues

- **Upstream:** a queue-or-steer follow-up setting that defaults to steer, a shared composer dispatch, one `t3_queue` action tool, and held queues after a Stop, a failure or a restart. Queue rows show who sent each message and offer send now, edit and remove; people no longer reorder them. A person's message from web or mobile releases a hold. Agent, server and scheduled messages held in a queue now release when the thread's newest run completes, unless a Stop reached that run; a person's stay held. An idle thread still starts an agent's message past the hold. A steer into a stopping run stays queued. Claude still steers with `priority: "now"`, and Cursor still steers by interrupting and restarting.
- **J5:** follows upstream's steering and queues. Agent deliveries queue behind a running turn by default, with the GPT 6 and Claude exceptions, and a sender may ask for `steer` or `restart` ([divergence D4](upstream.md)); `auto` is not offered, and the default is revisited in January 2027. A J5 delivery to an agent whose queue is held, idle or busy, resumes it and joins the back, so messages run in the order they landed, a person's held ones too. A delivery to an agent stopped on a usage limit, or after a failed worktree setup, waits as before. A refused peer steer joins the queue. Agents have upstream's queue tools, edit only messages they sent, and may still reorder.
- **Watch for:** D4 can go when upstream steers without cancelling running tool calls on Claude and without restarting on Cursor. The [Cursor change](https://github.com/pingdotgg/t3code/pull/28980) is open. [The change that queues agent sends to Claude](https://github.com/pingdotgg/t3code/pull/21158) is open and in a maintainer's hands; it would catch J5's Claude peer steers, which send `steer_active` as an agent, so landing it ends that exception unless J5 carries a bypass. [An open change](https://github.com/pingdotgg/t3code/pull/26842) stops steers cancelling a pending question or approval, including through J5's path. Upstream declined a resume tool in favour of the release on completion; J5's resume stays while upstream leaves a person's held messages behind an agent's.

## Long-running autonomy

- **Upstream:** a Limited state, snooze until the reset, opt-in auto-resume, scheduled tasks across environments including a one-off date and time, pull-request watches, webhook schedules held by the relay, self-settling, auto-settle opt-outs and settle scripts. Interrupted threads continue after a restart by default, stopping after three automatic restarts within five minutes; a continuation that fails before the provider accepts it retries twice, and its prompt tells the agent to check before repeating side effects. A parent's Stop reaches its delegated children across a restart. On Linux each agent runs in its own scope, and `service protect` keeps the server alive under memory pressure. Claude threads over 200,000 tokens can compact while idle.
- **J5:** follows all of it. A Crew seat may settle itself, and a Captain's settle carries its seats ([divergence D14](upstream.md)). A message from another agent holds a merged thread open ([divergence D30](upstream.md)). A stopped agent is not continued after a restart. J5 names its own systemd slice and protect drop-in. J5 keeps a queued-run watchdog; retire it if upstream's visible startup failures leave it with nothing to report.
- **Watch for:** continuation waking seats and Peer Agents into work their Captain or spawner has moved past, more likely now that failed continuations retry. A "before the cache expires" compaction, still beta, doing the same; J5 agents are root threads, so they qualify when it is on.

## Providers as packages

- **Upstream:** provider code lives in packages. `provider-core` holds the adapter contract, failure handling, the standing instructions, MCP provider sessions, the catalog and the subagent projection. Codex and Claude remain in the server; Cursor, OpenCode, ACP, the ACP Registry, Grok, Pi, Muse Code, Vercel's fx and, new, Kiro are packages. Source-control hosts and secret providers are packages too. A managed policy file can cap permission modes and lock settings for a whole machine.
- **J5:** J5's persona instructions, Crew-seat flag and native-resume fields are edits to `provider-core`, with one line in the OpenCode package. Its standing instructions live in a J5 folder inside `provider-core` ([divergence D1](upstream.md)). New providers are taken with no J5 work. J5 reads its managed policy from its own locations ([divergence D19](upstream.md)).
- **Watch for:** a way to supply instructions or runtime policy without editing a package or an adapter, such as a member on `ProviderHost`. There is none: `ProviderHost` did not change in this range, and managed policy has no instruction member.

## Skills

- **Upstream:** each provider snapshot reports installed skills, and the slash menu lists them. No install, catalog or cross-provider linking has shipped.
- **J5:** Settings → Skills installs catalog groups from a configured source into Codex and Claude homes, inspects each provider's skills, and links standalone skills across providers.
- **Watch for:** upstream installing or managing skills itself, which would make J5's catalog a source feeding upstream's mechanism. Four changes are open: [Settings → Tools](https://github.com/pingdotgg/t3code/pull/21817), which is a maintainer's and toggles skills and shared MCP servers; [browse and sync](https://github.com/pingdotgg/t3code/pull/24377); [bundled skills with install and update](https://github.com/pingdotgg/t3code/pull/28492), the closest to J5's catalog; and [per-model variants](https://github.com/pingdotgg/t3code/pull/27123).

## Playbooks and automations

- **Upstream:** scheduled tasks on an interval, once at a time, or from a webhook. Muse Code and Claude workflows, and `/goal`, are provider-native and keep no step progress in the app. Guided reviews are documents.
- **J5:** Playbooks are step tracking for agent-led work, with a library, persisted runs that agents advance through MCP tools, and progress on web and mobile. They carry no scheduling, git or worktree behavior.
- **Watch for:** upstream workflows or multi-step automations with durable progress kept by the app. None yet.

## Sharing a thread

- **Upstream:** "Share with guest", a Labs beta that works only over T3 Connect: a guest watches a thread live and sends messages the person approves or dismisses. A server is otherwise one person's. A managed policy can now forbid remote clients and Connect on a machine. Copy thread link gives a link to upstream's hosted app.
- **J5:** people, scopes and levels decide what each connection reaches ([People and access](features/people-and-access.md), [divergence D33](upstream.md)). Upstream's guest links are hidden, because J5 doesn't ship T3 Connect ([divergence D40](upstream.md)). A copied thread link points at j5.codes and grants nothing ([divergence D19](upstream.md)).
- **Watch for:** guest links working without T3 Connect, which would revisit D40. Upstream adding people, or per-thread access. Approved guest messages are close to a Viewer proposing a message that a writer sends or dismisses, which J5 has not built. Managed policy growing to carry people, skills or agent definitions, which would meet J5's plans for organization-wide sharing.

## Give-back

Fixes J5 carries that belong upstream are tracked in the give-back backlog. Three of our offers merged in this range (Reconnect on a switched-off environment, the wizard's project selection, device list warnings), and upstream fixed a fourth finding on its own (a finished thread staying under Working on mobile).
