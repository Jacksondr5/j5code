# Upstream convergence watchlist

Where upstream T3 Code is building toward the areas J5 owns. Each entry says what upstream has, where J5 stands, and what would make us adopt upstream's version or change our own. Rewrite this file at every upstream advance (see [Merging upstream](../process/upstream-merge.md)); the line below names the upstream release it was last checked against.

Checked against `pingdotgg/t3code` stable `v0.1.11` @ `59651c1761` (3,275 commits past `v0.1.7` @ `322f6544df`). Open pull requests read on 2026-11-22.

## Agent-to-agent messaging and control

- **Upstream:** the orchestrator MCP toolkit can send into another thread, wait on it, interrupt it and launch threads (`t3_thread_send`, `t3_thread_wait`, `t3_thread_interrupt`, `t3_thread_launch`, `create_threads`), answer another thread's questions (`t3_pending_request`) and reconfigure it (`t3_thread_configure`). Every tool declares who may call it, and thread-only tools are hidden from an outside client, which signs in with OAuth. `t3_thread_send` takes `freshContext`, and a person's `/clear` starts a fresh provider session in the same thread. `send_to_user` shows content to the person in the agent's own thread. A session that asks for deferred listing gets a few tools and `tool_search` for the rest. Messages from agents carry `senderThreadId`, and since v0.1.11 those from a linked environment name the thread that sent them too; they fold into one-line rows and show their sender while queued. The model reads a line before each such message saying who sent it, "not the user". A delegated child's question wakes its parent, steering into the running turn when the provider can steer without interrupting tools and otherwise queueing; a completion wake names the child. A person can answer a delegated child's approvals from the parent thread. `t3_pending_request` still cannot approve a permission request.
- **Linked environments** (a Labs beta, off by default, on each machine): two servers link over any route that reaches them, and an agent then names another machine's `environmentId` on thread, project and queue tools, or delegates there. Work a link starts is fenced to that link below full access. Since v0.1.11 a link renews while it is used and ends after 30 days unused; "Link several…" and `t3 environment link --from` link several machines at once; a machine the app knows is linked only at the addresses it has; and a stalled handshake fails after a bounded wait. Tool calls over a link need a direct connection, and upstream plans no poll mode. [Import](https://github.com/pingdotgg/t3code/pull/16731) and [handing a thread off](https://github.com/pingdotgg/t3code/pull/16751) are still open.
- **J5:** a ledger for each project, addressable participants, Exchanges, Inbox and delivery receipts. J5 follows upstream's access model and outside-agent sign-in ([divergence D2](upstream.md)). It hides upstream's send and bulk-create tools, so `freshContext` is out of agents' reach and a clean start is a fresh agent or seat with a brief. It admits wait, gives interrupt J5's Captain rule, admits every tool upstream added at v0.1.11, holds `tool_search` to what its caller may see, admits launch only for link sessions, and hides its own thread-only tools from outside clients as upstream hides its own. Agents are told that `send_to_user` shows something in their thread and that anything the person must act on is an Inbox ask. J5's envelope is the only sender line on a J5 delivery; upstream's line stays on upstream's own sends ([divergence D48](upstream.md)). An agent in a side chat is refused J5 messaging, as a subagent is. A Crew seat asks its Captain. Native questions on J5-spawned Peer Agents or live seats notify their placement parent by queueing, and reach the Inbox as links; delegated children keep upstream's reactor and approval roll-up. J5 peering stays the ledger's path between servers. On web and desktop a person sets up peering and upstream's links together, as one link for a pair of servers, with messages both ways and a level for actions in each direction; actions renew with use as upstream's do, and "Link several…" is not in that flow for now ([divergence D47](upstream.md)). Same-machine servers link at loopback addresses, which upstream refuses ([divergence D49](upstream.md)). Peering polls for messages, so a sleeping or firewalled machine still gets them later; a server that polls holds a line so that tool calls reach it, and a machine that does not answer, a stalled handshake included, fails with its own code ([divergence D46](upstream.md)).
- **Watch for:** reply or ask semantics, an inbox, or responder attribution upstream. Child question or approval routing extended to threads an agent started that aren't delegated children. An outside client that can _receive_ messages. Approval answering by agents returning. Handing a thread off or importing one across machines landing, which would overlap J5's delivery across servers and is the moment to reconsider peering. A poll mode for links. A two-way link or removal on both machines, either of which J5's link flow could hand back to upstream; linked environments leaving Labs. Upstream's sender line gaining a case, or a structured sender field the model reads, which could carry J5's envelope instead (D48). Changes to "Link several…" that would decide how it fits J5's flow. A way for a link to renew its messages' half too, or for peering's long-lived credential to follow links' rolling renewal. An admission rule for `tool_search`'s direct set or a new deferring provider, which must stay within what J5 admits.

## Launch, workspaces and parallel agents

- **Upstream:** workspace-aware launches, configurable branch names, tracked worktree setup. A "No project" project, which a thread can turn into a real project where it stands. Multi-model send. `delegate_task` can give a child its own worktree, and can run on a linked environment. Providers can be switched per project. Projects can be pinned and archived. Storage cleanup removes settled threads' worktrees. Threads can carry tags, with no UI or MCP tool. Side chats are hidden forks with their own composer in the right panel, archived with their parent since v0.1.11. An open delegated task selects its parent's sidebar row, and tasks delegated from a linked environment stay out of `t3_thread_list`. Pi's workflow, chain and parallel members show as subagents.
- **J5:** `j5_spawn_agent` and Crews create Peer Agents with briefs; every one names its workspace, prepared through upstream's ThreadLaunch when it is new. `j5_spawn_agent` can start a Peer Agent on another J5 machine, over a link. J5 doesn't give agents `t3_thread_launch` or `create_threads`. `delegate_task` takes upstream's worktree option as shipped, and is hidden from outside clients. Multi-model send is refused from a persona draft. Side chats are treated as subagents are. A thread turned into a project keeps its participant where it was until J5 re-homes it.
- **Watch for:** coordination of fanned-out threads, or tags gaining a UI or an MCP tool, either of which comes close to Crews. Delegated children listed in the sidebar or Cmd+K on their own: a delegated child with its own worktree and composer is already a Peer Agent in all but discoverability. Remote launch and delegation leaving the Labs beta, which would meet `j5_spawn_agent` on a peer server.

## Lineage, subagents and fleet views

- **Upstream:** a thread-details panel with Lineage (including remote delegates, which no longer split from the list, Claude workflows by phase and a separate Side chats section), hover cards, per-turn subagent cards, a breadcrumb to the parent. `thread.stop` interrupts the turn, holds the queue, ends pull-request watches and stops delegated children. Every interrupt is bounded; a provider that ignores Stop shows "Agent not responding" with Force stop. The sidebar's Waiting covers a thread blocked on another thread, and any pending question moves a thread to Input. Diagnostics has a resource timeline, and OpenTelemetry export carries run and resource metrics. Upstream's copy calls the sidebar's active section "the inbox", which is not J5's Inbox.
- **J5:** placement and provenance, the Fleet page, sidebar spawned-children and Crew chips, persona identity on rows. J5 adds its command relations to upstream's Lineage through one delegate: a thread's placement parent and Crew Captain, and the Peer Agents and Crew seats under it. Upstream subagents stay upstream's rows. Re-check the delegate whenever upstream's Lineage changes shape. `t3_thread_interrupt` with `stop: true` and Crew stop send `thread.stop`.
- **Watch for:** cross-thread grouping beyond one thread family, or an attention queue across threads; upstream's change to sort the sidebar as a queue closed unmerged. Run metrics in ordinary thread or fleet navigation rather than Diagnostics, which would come close to the Fleet page.

## Handoffs and history transfer

Two different things share the word "handoff". J5 docs call upstream's history transfer a **context handoff** and J5's persona document a **handoff artifact**.

- **Upstream:** context handoffs move a budgeted slice of history into a new provider conversation on a model or provider switch, a fork, or a portable restart. When a native resume fails, or a resumed conversation can't hold the history it must be handed, upstream starts a fresh conversation and, since v0.1.11, shows a "Context handoff" divider for it. A Codex thread another client is writing to fails with a message naming that client. Claude reports a conversation it no longer has, and the next send starts fresh. A provider that can't roll back starts fresh after Edit from here, and Antigravity recovers a broken thread the same way. `/clear` and scheduled tasks that start a fresh session each run are explicit fresh starts.
- **J5:** persona handoff artifacts under `handoffs/`, with a nudge worker and a composer chip. J5 follows upstream's fresh starts and divider as shipped (D6, retired).
- **Watch for:** fresh starts upstream adds without its divider, which would bring back the silent fresh start D6 was written against.

## Steering and queues

- **Upstream:** a queue-or-steer follow-up setting that defaults to steer, a shared composer dispatch, one `t3_queue` action tool, and held queues after a Stop, a failure or a restart. Queue rows show who sent each message and offer send now, edit and remove. A person's message from web or mobile releases a hold; agent, server and scheduled messages held in a queue release when the thread's newest run completes, unless a Stop reached that run, and a person's stay held. A send to an idle thread with a queue waits behind it, and resuming a queue no longer bypasses a failed worktree setup. A steer into a stopping run stays queued. Since v0.1.11 every Claude steer waits for the running tool calls and is read in the same turn, and a steer Claude drops runs as the next turn in its place; agents' messages steer into Codex and Claude turns by default. Cursor steers a live run without restarting it, but still reports that steering interrupts tools, so agents' messages to it queue.
- **J5:** follows upstream's steering and queues, with upstream's Claude adapter whole. Agent deliveries queue behind a running turn by default, with the GPT 6 and Claude exceptions, and a sender may ask for `steer` or `restart`; `auto` is not offered yet ([divergence D4](upstream.md)). The condition J5 set for dropping that default is met, and following upstream's `auto` is the next step. A J5 delivery to an agent whose queue is held, idle or busy, resumes it and joins the back, so messages run in the order they landed, a person's held ones too. A delivery to an agent stopped on a usage limit, or after a failed worktree setup, waits unsent. A refused peer steer joins the queue. Agents have upstream's queue tools, edit only messages they sent, and may still reorder.
- **Watch for:** Cursor's capability saying its live steer no longer interrupts tools, which changes what `auto` does there. A steer or restart that keeps a pending question or approval; the change that would have done that closed unmerged. Release of a whole held queue, a person's messages included, on any new message; J5's resume stays while upstream leaves a person's held messages behind an agent's.

## Long-running autonomy

- **Upstream:** a Limited state, snooze until the reset, opt-in auto-resume that survives a restart, scheduled tasks across environments including a one-off date and time and a mode that starts a fresh session each run, pull-request watches, webhook schedules held by the relay, self-settling, auto-settle opt-outs and settle scripts. Auto-settling skips a thread with a pending pull-request watch. Interrupted threads continue after a restart by default, stopping after three automatic restarts within five minutes, and restart recovery wakes delegated children waiting on background work. A parent's Stop reaches its delegated children across a restart. On Linux each agent runs in its own scope, and `service protect` keeps the server alive under memory pressure. Claude threads over 200,000 tokens can compact while idle, but not in the middle of delegated work.
- **J5:** follows all of it. A Crew seat may settle itself, and a Captain's settle carries its seats ([divergence D14](upstream.md)). A message from another agent holds a merged thread open ([divergence D30](upstream.md)). A stopped agent is not continued after a restart. J5 names its own systemd slice and protect drop-in. J5 keeps a queued-run watchdog; retire it if upstream's visible startup failures leave it with nothing to report.
- **Watch for:** continuation waking seats and Peer Agents into work their Captain or spawner has moved past. A "before the cache expires" compaction, still beta, doing the same; J5 agents are root threads, so they qualify when it is on. A placement-aware continuation rule that would cover idle Crew seats and stopped Captains.

## Providers as packages

- **Upstream:** provider code lives in packages. `provider-core` holds the adapter contract, failure handling, the standing instructions, MCP provider sessions, the catalog and the subagent projection. Codex and Claude remain in the server; Cursor, OpenCode, ACP, the ACP Registry, Grok, Pi, Muse Code, Vercel's fx and Kiro are packages. Source-control hosts and secret providers are packages too. A managed policy file can cap permission modes, lock settings and turn off the preview tunnel for a whole machine. `ProviderHost` gained readiness, agent tracking and a compatibility lookup in this range.
- **J5:** J5's persona instructions and Crew-seat flag are edits to `provider-core`; its standing instructions live in a J5 folder inside it ([divergence D1](upstream.md)). The native-resume fields are gone with D6. New providers are taken with no J5 work. J5 reads its managed policy from its own locations ([divergence D19](upstream.md)).
- **Watch for:** a way to supply instructions, per-agent policy or tool approval without editing a package or an adapter, such as a member on `ProviderHost`. There is none yet, and managed policy has no instruction member.

## Skills

- **Upstream:** each provider snapshot reports installed skills, and the slash menu lists them, including managed Claude skills, plugin skills and skills a session hook links. No install, catalog or cross-provider linking has shipped.
- **J5:** Settings → Skills installs catalog groups from a configured source into Codex and Claude homes, inspects each provider's skills, and links standalone skills across providers.
- **Watch for:** upstream installing or managing skills itself, which would make J5's catalog a source feeding upstream's mechanism. Two changes are open: [Settings → Tools](https://github.com/pingdotgg/t3code/pull/21817), which toggles skills and shared MCP servers, and [bundled skills with a settings manager](https://github.com/pingdotgg/t3code/pull/28492), the closest to J5's catalog. Browse-and-sync and per-model variants closed unmerged.

## Playbooks and automations

- **Upstream:** scheduled tasks on an interval, once at a time, or from a webhook, each run in its own thread or in one thread with a fresh session. Muse Code and Claude workflows, Pi's workflows, and `/goal` are provider-native and keep no step progress in the app. Guided reviews are documents. The Issues page and the issue tools link issues to threads.
- **J5:** Playbooks are step tracking for agent-led work, with a library, persisted runs that agents advance through MCP tools, and progress on web and mobile. They carry no scheduling, git or worktree behavior, and their tools are hidden from outside clients.
- **Watch for:** upstream workflows or multi-step automations with durable progress kept by the app, such as an issue-to-pull-request flow that records its steps. None yet.

## Sharing a thread

- **Upstream:** "Share with guest", a Labs beta that works only over T3 Connect: a guest watches a thread live and sends messages the person approves or dismisses, now from mobile too. Other features need Connect as well: "Use T3 Code in another app (MCP)", the Welcome page's phone section, approval of new Connect devices, and approving an agent's sign-in through Connect. A server is otherwise one person's. A device paired directly holds a session bound to a key it keeps, and renews it itself. A managed policy can forbid remote clients and Connect on a machine. Copy thread link gives a link to upstream's hosted app.
- **J5:** people, scopes and levels decide what each connection reaches ([People and access](features/people-and-access.md), [divergence D33](upstream.md)). A key-bound device renews with upstream's renewal, and is paired again by hand after a change of level, for now. Every feature that needs T3 Connect is hidden, because J5 doesn't ship it ([divergence D40](upstream.md)). A copied thread link points at j5.codes and grants nothing ([divergence D19](upstream.md)).
- **Watch for:** guest links or the other Connect features working without T3 Connect, which would revisit D40, and each new feature that works only over Connect, which D40 hides. A renewal that can re-issue a key-bound session with new permissions, which J5's renewal after a change of level could use (D33). Upstream adding people, or per-thread access. Approved guest messages are close to a Viewer proposing a message that a writer sends or dismisses, which J5 has not built. Managed policy growing to carry people, skills or agent definitions.

## Names, install and translations

Not J5's own areas, but places where each advance carries J5's names through upstream's code.

- **Upstream:** the release executable is `t3`; a fresh desktop install links it on first launch, and the command and the service unit follow an update from the app. Its launchers report protocol 4 since v0.1.11 and still run under protocol 3. Windows has a background service, a Task Scheduler task. The web, desktop and mobile apps are translated into nine more languages, from catalogs keyed by each English source string.
- **J5:** the executable is `j5`, and J5's protocol 4, which marks the rename, is upstream's 4 too; J5 still refuses to move a protocol-3 server and tells an older target it runs under 4 ([divergence D28](upstream.md)). The desktop app links `j5` on first launch, and Add to PATH writes the installer's marked line. Upstream's Windows service runs under J5's names, not yet tried on a Windows machine ([divergence D20](upstream.md)). J5 rebrands upstream's English source strings and carries their translations to the new keys with a script at every advance; J5's own screens are in English for now ([divergence D25](upstream.md)).
- **Watch for:** upstream's launcher protocol moving past 4, which J5 follows while keeping 3 refused, and any code that finds the executable by name. A way to substitute the product name when a string is shown rather than in its source, which would let J5 drop the re-keying. New OS-facing names, such as a task, a folder or a label, that would collide with an installed T3 Code.

## Give-back

Fixes J5 carries that belong upstream are tracked in the give-back backlog. Twelve items J5 followed up after its offers landed upstream are in this range, among them `t3 update` checking the database before it switches builds, the command and the service unit following an update from the app, and mobile's answered question without its raw item. Upstream also shipped the two changes J5 had carried as temporary patches: the `gh` default remote (D31) and a visible fresh start (D6).
