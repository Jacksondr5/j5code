# Product glossary

The J5 product vocabulary of record. One entry per term, with a pointer to the defining document — the pointer is authoritative when detail matters. Terms inherited unchanged from T3 Code (project, thread, turn, environment, checkpoint, provider…) live in the upstream glossary at `docs/internals/glossary.md`; this file covers what J5 adds or redefines. **Writing convention:** named product concepts are written Title Case — Squadron, Crew, Captain, Manifest, Role, Playbook, Memo, Exchange — so readers know it's our concept, not the generic word; descriptive terms (fleet, agent, participant, inbox, ledger, dashboard) stay lowercase, and code identifiers are unaffected. Update this file as terms settle — a stale glossary is worse than none.

## The agent organizational family

We use a civil-nautical theme to make onboarding users to these concepts easier.

| Term         | Meaning                                                                                                                                                                                                                                                                                              |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fleet**    | The totality — all of a user's agents across every connected server (the merged client view, X2). Never a sub-grouping.                                                                                                                                                                              |
| **Squadron** | User-created grouping of agents, artifacts, PRs, and their ledger around a large or long-running initiative. A grouping, never a boundary; single home, immutable membership; lives entirely on one server (X1). Formerly code-named "epic" (renamed 2026-08-17). Defined in `features/squadron.md`. |
| **Crew**     | A group of agents spawned as a unit from a Crew definition: fixed membership, entirely within one Squadron, archived only as a unit. The hands running one piece of work. Defined in `features/crews.md`. (R12–R17)                                                                                  |
| **Role**     | A reusable, user-authored definition of a kind of agent: identity/prompt content, model + reasoning allowlist, skill allowlist, posture. Spawnable solo or composed into Crew definitions. Defined in `features/roles.md`. (R28)                                                                     |
| **Manifest** | Implementation vocabulary, not a separate concept: the artifact form of a Crew definition — composes Roles into a Crew with their wiring. The user's content — git-versioned, portable, shareable by construction. (R12, R28)                                                                        |
| **Captain**  | Derived role archetype, not a platform entity: any agent with Crews placed under it. Runs Crews, serves as tie-breaker; never a communication router. Captaincy follows placement. Defined in `features/crews.md`. (R18–R22)                                                                         |

## Spawning (settled 2026-08-24; worklog: `../worklog/spawn-terminology-session-2026-08-24.md`)

| Term               | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Subagent**       | Adopts upstream's own word. A worker an agent runs inside its own provider session (Claude Task workers, Codex collab children, Cursor task subagents): an **un-addressable child** — same provider only, dies with the parent's session, can never be moved out of the parent's tree, almost always created for a one-off task. What the user _sees_ varies by harness (summary block to a mirrored read-only view); what never varies is that the user cannot talk to it. Not a participant; never in the ledger (D1). **The platform cannot control Subagent creation and does not try** — it only observes what harnesses surface. _(Implementation-vocabulary caveat: upstream code also labels `delegate_task` children "subagents" (`origin: "app_owned"`) — that usage is not ours.)_ |
| **Peer Agent**     | J5's term (no upstream collision). An agent spawned by another agent as a **full citizen**: the user cannot tell it from any other agent without checking provenance — full conversation visibility, direct interaction, independently managed lifecycle, any provider. All platform spawning law governs Peer Agents and only Peer Agents: R21 placement, Squadron inheritance, the creation-time Registrar, ledger participanthood.                                                                                                                                                                                                                                                                                                                                                         |
| **Spawn**          | The verb for creating either kind, always qualified — "spawn a Subagent," "spawn a Peer Agent." Unqualified "spawn" in J5 documents means a Peer Agent spawn.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Spawning Guide** | The user-authored guide consulted at the moment of spawning: selection guidance (provider/model/reasoning per kind of work, which Role to pick) and brief conventions. Platform ships the mechanism and the factual catalog; the judgment layer is the user's ([spawning-guide.md](features/spawning-guide.md), SP1–SP2, 2026-08-30).                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

## Communication (A2A)

| Term                       | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Participant**            | Anything with its own thread: main agents, agent-created child agents, and humans. Provider-native subagents are not participants. (D1)                                                                                                                                                                                                                                                                                                                                                                                     |
| **Agent**                  | An LLM participant.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Node**                   | A participant as rendered in the communication graph.                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Exchange**               | The reply obligation: a reply-expected send mints an `exchangeId`; idempotent open per sender→receiver pair; one reply closes everything on it; the sender judges completeness at closure (R3). States: open / stalled / answered / dropped. Never called a "thread" — an exchange travels _through_ T3 threads. (D9)                                                                                                                                                                                                       |
| **Communication ledger**   | The per-squadron append-only event log — source of truth for all A2A state; rows never edited, corrections are new rows; survives restarts. (A2A M1)                                                                                                                                                                                                                                                                                                                                                                        |
| **Projection**             | A derived, materialized, disposable view over the ledger (graph, inbox, stall report, playback). Wipe-and-rebuildable, never authoritative.                                                                                                                                                                                                                                                                                                                                                                                 |
| **Silence notice**         | A platform-authored fact bundle appended when an agent says nothing — turn ended, no closing reply, open outbound exchanges listed structurally. Labels (awaiting-human, blocked-on-peer…) are projection policy, not ledger fact. (D6, R4)                                                                                                                                                                                                                                                                                 |
| **Envelope**               | The platform's per-channel prompt wrapper teaching protocol semantics at the moment of action; carries measured time facts (R25). Versioned config the user owns.                                                                                                                                                                                                                                                                                                                                                           |
| **Exchange vs delegation** | "Delegation" (D1's term) = a Peer Agent spawn plus a result Exchange — expressible entirely with existing primitives (spawn + `expect_reply`). Upstream's `delegate_task` realizes it less capably (sidebar-hidden lineage, subagent labeling, spawn requires an active parent run); **direction (2026-08-24): exclude `delegate_task` from the J5 product surface** — disposition of the inherited tool sits with the Director. Provider-native Subagent work never appears in the ledger. (D1; spawn-terminology session) |

## Humans and attention

| Term                        | Meaning                                                                                                                                                                                                                                                                                    |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Person id**               | The durable local identity (`human:<id>`) minted at first run, used in every ledger row; external auth binds to it later. Nothing may assume exactly one human (R29's multi-human invariant). (R9)                                                                                         |
| **Inbox**                   | The obligation queue: open exchanges addressed to a person, urgency-ranked. Every item blocks a sender. Pure — no inferred mail, no auto-promoted stalls, no memos. (M4, R5, R26)                                                                                                          |
| **Observability dashboard** | Where the human investigates "why isn't X done": stalls, blocked-on-peer chains, liveness. (R5)                                                                                                                                                                                            |
| **Backlog pane**            | The pull-based view of all agents' memos. Third sibling to the inbox and observability views — shared UI allowed, shared data model never. (R26)                                                                                                                                           |
| **Memo**                    | A small self-addressed message an agent stores via platform tool: non-blocking, always user-visible, per-agent, agent-cleared, optionally deferred via `resurface_after` — the one platform-initiated re-injection. The v1 agent data primitive. Defined in `features/memos.md`. (R31–R35) |

## Structure and work

| Term                | Meaning                                                                                                                                                                                                                                                              |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Org placement**   | The display-tree position of an agent; equals spawner at spawn ("you command what you brief", R21 amending D10); human-only re-parent is the sole divergence. Cascade operations follow placement.                                                                   |
| **Playbook**        | User-authored step content a Role or Crew executes; the platform holds the step pointer (advanced by tool call) and delivers each next step fresh, per participant. Engine = platform, steps = content. Defined in `features/playbooks.md`. (R27; backlog candidate) |
| **Shared Squadron** | The multi-user capability: several people on one server sharing Squadrons (shift handoff, two humans before one agent). Distinct from cross-device (X1–X5) and federation (X4). Defined in `features/shared-squadrons.md`. (R29; backlog candidate)                  |
| **Epic**            | Historical name for squadron in pre-2026-08-17 documents; read as squadron. Inspired by Traycer's own epic concept in the design workspace.                                                                                                                          |
